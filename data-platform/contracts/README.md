# v1 数据契约与指标口径

本阶段固定6张来源表及列白名单，见 [source-contract.json](source-contract.json)。不抽用户表、手机号、token、图片和Outbox错误文本；仅抽订单相关Outbox种类。ID使用十进制字符串，金额使用整数分或Decimal(38,0)，NULL金额保留未知。源TIMESTAMP在UTC会话抽取为带Z时间，SQL日切显式转换Asia/Shanghai。

创建事实：一行order_id，按创建日归属，依据订单快照列，绝不使用现价补算。快照列本身不证明创建时真实性，snapshot_provenance先保留unknown。订单状态放在单独的实际快照事实中；不能用今日状态还原过去日终。

事件事实：一行event_id，按发生日归属，保留处理时间。v1只接受CREATED/PAID/CLOSED；同订单多个付款事件暂拒绝发布，避免计数去重而金额重复求和。若后续业务允许多次真实支付，必须先版本化契约。免费领取状态2不等同付款；本项目无真实支付流水，本地仅演示模拟付款。

店铺日报粒度为业务日+shop_id+source_env，指标包括创建订单/当日去重人数、已知创建金额/未知笔数、免费笔数、付款事件订单/已知金额/未知笔数、关单事件数。日付款与日创建来自不同集合，不计算两者相除的“付款率”。跨日去重人数不可相加。

ADS提供店铺日订单排行、实际快照状态分布、券创建cohort表现。券cohort中已知正金额普通券的取消数量/分母单独输出，必要时才由展示层计算比例；未知金额不猜为付费。退款和核销只有状态快照，不伪造缺失事件和净收入。

无关单原因字段时输出unknown，暂不修改Java业务契约。缺维和未知金额给出质量警告与数量；孤儿事件、重复主键、非法类型、数据损坏、订单与汇总不符为阻断错误。未投影事件允许以警告发布，报表必须结合质量报告阅读，不得声称数据最终完整。

抽取时点由真实事务开始时采集，用户不能手填历史snapshot_as_of。客户端取得快照的时间近似标记，不是精确提交时间或GTID位点。DDL需源库管理方排除；抽取器不持有全局锁。合成三批的scenario_as_of仅是明确标注的情景时钟。

完整快照→DIM/DWD保留该快照所有记录；--biz-date只筛选本次DWS/按日ADS。状态报表记录_snapshot_as_of，属于快照截点而不是日终。每次run_id对应不可变版本，catalog按业务日指向最近成功版本；失败不改变指针。暂不支持对象存储/多主机并发协议。


## 付款时间契约

模拟付款由 MySQL NOW(3) 写入 TIMESTAMP(3) pay_time，同事务付款 Outbox 的 created_at 复制该值，投影沿用该业务发生时间；enqueued_at 独立记录入队时间。V10 迁移将旧入队时间近似回填为旧 created_at，不能据此还原真实历史排队耗时，也不会改写已有事件历史。JDBC serverTimezone 必须与数据库会话解释一致；本地默认和 Compose 均为 Asia/Shanghai，抽取会话显式使用 UTC。不要在 +08 会话中直接把 UTC_TIMESTAMP 当本地时间写入 TIMESTAMP。

门禁检查整个输入快照，不能只修日报而忽略历史异常。付款时间缺失、绝对差值达到 60000ms、或上海业务日不一致时阻断；同业务日差值在 [1000,60000)ms 时告警，小于1000ms正常。阈值是本地兼容旧记录的契约，不代表接受分钟级时钟漂移。quality.json 保留缺失、告警、阻断数量和最大偏差；严重时区错误不能仅靠放宽阈值发布。
