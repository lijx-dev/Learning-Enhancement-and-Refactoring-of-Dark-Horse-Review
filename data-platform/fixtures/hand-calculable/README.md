# 可手算优惠券订单样本 v1

这是一套**纯合成数据夹具**，用来学习和验收 SQL、快照、金额口径、时间归属和事件晚投影。不是线上订单，也不是经 API 完整回放的业务验收。14 笔核心订单刻意保持小规模；先手算正确，再谈放大数据量。

- [scenario.json](scenario.json)：逐笔场景、固定 ID/时间/状态变更；金额单位分。
- [expected.json](expected.json)：独立人工答案，不由生成器计算或覆盖。
- [metrics.sql](metrics.sql)：同一组查询分别在 SQLite、MySQL、Spark 执行并与人工答案比较。
- [fixture.py](../../tools/fixture.py)：确定性生成、文件 SHA256、SQL 对账、隔离库导入和 Spark/Parquet 验证入口。

## 手算答案

创建口径以订单表为准，不依赖投影事件是否到齐。

| 创建日 | 店铺 | 笔数 | 去重用户 | 已知金额/分 | 未知金额笔数 | 免费笔数 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 10-29 | 1 | 4 | 3 | 1000+2000+0+1000 = **4000** | 0 | 1 |
| 10-29 | 2 | 2 | 2 | 1500+3000 = **4500** | 0 | 0 |
| 10-30 | 1 | 3 | 3 | 1000+1000 = **2000** | **1** | 0 |
| 10-30 | 2 | 5 | 5 | 3000+1500+3000+3000+3000 = **13500** | 0 | 0 |

10-29 共6笔、5人，8500分；10-30 共8笔、8人，已知15500分，另1笔未知。全部14笔已知金额24000分，不能把它写成“14笔完整金额240元”，也不能用当前券价重算。两天用户合计去重10人，而每日去重相加为13人，不能当总 UV。

按事件发生日统计模拟付款：

| 发生日 | s1 | s2 | s3 |
| --- | --- | --- | --- |
| 10-29 | O01+O04：2笔、2500分 | 同s1 | 同s1 |
| 10-30 | 截点前无事件，不输出行 | O05+O07+O11+O13+O14：5笔、15000分 | 再补O08：**6笔、16000分** |

O08 虽10-31才投影，仍归10-30；因此s3改变的是旧日期付款统计，不是把它算到10-31。s2 店铺1尚无当日付款事件行，不代表它真实没有发生付款。O11已退款仍有曾经付款事件，不能因当前状态6把历史付款抹掉，也不能拿这张表算净收入。

关单：10-29 1笔（O02），10-30 2笔（O06/O10）。虽然情景说明中知道预设动机，当前源事件不含原因，分析输出仍须保留 unknown，不偷读情景 note 做真实归因。

状态分布：s1 为 `{1:2, 2:3, 4:1}`；s2/s3 为 `{1:2, 2:6, 3:1, 4:3, 5:1, 6:1}`。其中状态2的6笔含1笔免费券，因此不能直接得出“6笔支付”。

附带秒杀样本：活动21总库存3，s1已有1笔成功预约、余2；s2/s3成功预约2、余1。“成功预约”仅说明订单已落库，O09仍待付款，不等于2笔支付成功。

## 使用与验证

在项目根目录顺序执行：

```powershell
python -X utf8 data-platform/tools/fixture.py check
docker --context desktop-linux compose -f dev/local/compose.yml up -d --wait mysql
python -X utf8 data-platform/tools/fixture.py mysql
docker --context desktop-linux compose -f dev/local/compose.yml run --rm --no-deps spark --master "local[2]" --driver-memory 768m --conf spark.sql.shuffle.partitions=2 /workspace/data-platform/tools/fixture.py spark
```

check 生成并冻结 `target/warehouse-fixtures/hmdp_hand_v1/s1,s2,s3/` 的9张来源表 JSONL 和 SHA256 清单，执行 SQLite 查询对账；相同输入再次生成逐字节不变，已有不同内容会拒绝覆盖。expected.json 是单独人工答案，不能由生成器覆盖。生成文件与报告不进 Git。

mysql 仅写 `hmdp_warehouse_fixture`，从 hmdp 的真实迁移后表结构 CREATE LIKE，带所有者标记；重复执行先核对标记，再事务替换样本表。它顺序导入s1/s2/s3并逐次对账，最终库保留s3，不改 hmdp 或 hmdp_optimization_test。库内固定场景时钟，避免数据库默认时间随每次导入变化。连接仅限本项目 mysql 容器，凭据从容器已有环境读取。

SQL 视图：`fixture_orders/fixture_history/fixture_outbox`。例如查看14笔：`SELECT id,status,pay_value_snapshot FROM hmdp_warehouse_fixture.tb_voucher_order ORDER BY id;`。原应用仍连 hmdp，因此原页面不会自动显示此隔离库；避免启动原应用扫过这些历史合成订单造成自动关单。

spark 对同一份文件执行相同SQL，对照人工答案，验证字符串ID、Decimal金额、分区Parquet；每批覆盖写两次，检查数量/金额/ID不变。读取不经过数据库，验证的是冻结样本计算，不是新的完整抽取流水线。

本夹具尚未覆盖 unsigned 上界、损坏文件、冲突重复事件、并发补数与故障发布；不把这些待建设项写成已验收。当前SQL假定本样本每订单最多一个付款事件；正式流水线需要定义重复/冲突事件处理后才能复用到任意数据。
