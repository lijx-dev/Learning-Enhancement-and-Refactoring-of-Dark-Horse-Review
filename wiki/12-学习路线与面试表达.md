## 1. 先学闭环，不先背组件名

第一阶段：跑起来、正常登录、查店铺、领普通券。理解 HTTP、JSON、Controller/Service/Mapper、数据库行与 Redis Key。能在代码中找到一个页面按钮背后的接口。

第二阶段：学习 Redis实战篇的核心推导。亲自说明穿透/击穿/雪崩的差别，写出条件扣库存的判断，说明为什么解锁必须校验 owner、为什么 Feed 要游标翻页。

第三阶段：把当前扩展与课程对照。看五层缓存如何防旧回填，Stream 如何交接给持久 Outbox，RocketMQ 如何去重，Kafka 如何先提交数据库再提交 offset。

第四阶段：验证与表达。读隔离测试，尝试在测试环境复现重复请求、重放和恢复；讲清一个真实结果与它不能证明的范围，再考虑增加新功能。

## 3. 把一个亮点讲成能连续追问的答案

<a id="section-03-01"></a>

### 缓存：从一个具体错误讲到实现约束

场景是店铺从“老店名”改为“新店名”。旧查询已经读到老值，但还没写缓存；更新操作先删了缓存，随后旧查询把老值写回来。只讲“更新数据库后删缓存”无法解释这个窗口。

第一层回答讲顺序：查询读版本 v；失效让版本递增；回填时校验读取时的版本仍等于当前版本。旧查询的 v 落后，脚本拒绝它写入。相关实现见 [05 章](05-五层缓存与一致性.md)。

第二层回答讲锁：版本防数据世代落后，owner 防旧锁持有者在租约过期后覆盖新持有者。两项校验解决不同问题，不能只检查其中一个就宣称完整保护。

第三层回答讲多层：请求内缓存生命周期仅限本次请求；Caffeine 是每实例本地副本；Memcache 用版本组成地址并保留源到期时间；Redis 存共享值和版本。缓存层次变多，数据寿命不能因向另一层复制而无限延长。

第四层回答讲限制：在途请求可能已经拿到旧结果；Pub/Sub 通知可能丢；CDC 有延迟。当前方案防特定旧回填并约束副本寿命，不承诺所有实例每一瞬间都读到最新数据库值。

面试时按“出错时序 → 校验规则 → 代码位置 → 已有测试 → 仍有边界”展开。这样别人追问锁、版本或通知，你仍然在解释同一个问题。

<a id="section-03-02"></a>

### 秒杀：用库存为 2 的活动说明责任交接

先假设三个不同用户几乎同时抢同一活动。Lua 按串行执行效果检查资格与库存，最多两个预占成功，第三个返回售罄。成功的脚本还要把订单身份写进映射与 Stream，否则 Java 在返回后崩溃时，只有库存变少而没有工作记录。

接下来问“消息进 Stream 以后数据库就有订单了吗？”答案是还没有。Stream 消费者先登记数据库预约，再持久交接到 Outbox。交接成功后才 ACK，由数据库任务接续恢复；交接失败则保留 pending。随后 MQ 消费者再做条件扣库存与订单保存。

最后问“失败就加回库存可以吗？”需要确认旧失败对应的 orderId 仍拥有这个 userId 的资格，避免旧任务释放新订单的预占；成功订单也不能随意补偿。当前指定补偿会检查身份，复核任务需要先查事实。详见 [08 章](08-秒杀Lua与RedisStream.md)。

这一轮最好自己画出四个位置：Redis 预占、Stream、数据库预约/Outbox、正式订单。把“哪个位置崩溃，下一次从哪里继续”逐个写出来。

<a id="section-03-03"></a>

### Kafka：用同一个 eventId 被投递三次解释去重

Kafka Producer 的幂等发送不能直接代表 MySQL 统计不会重复增加。消费者可能在数据库提交后、offset 提交前退出，下一次读到相同事件。

当前聚合在同一数据库事务里先登记 eventId，再更新分钟桶和登录用户记录。原身份的重复事件不再加计数；同一个 ID 携带不同身份或动作则拒绝。事务成功之后才提交 offset。这里的重点是“数据库效果可去重”，不是宣称所有系统只有一次投递。

假设 A 用户在两个分钟各访问一次，B 用户访问一次，匿名用户访问一次：PV=4，登录 UV=2。不能把每分钟 UV 相加成 3，也不能把匿名浏览当作一个已识别登录用户。已有具体测试和手算见 [10 章](10-Kafka行为分析与热榜.md)、[13 章](13-测试监控与故障排查.md)。

## 6. 简历如何写得可验证

可以围绕三条主线写，保留你实际做过的内容：

- 为店铺与券元数据设计多层缓存、短期本地副本和版本回填校验，减少热门读取对 MySQL 的重复访问；用请求采样与隔离 HTTP 对比验证效果。
- 构建 Lua 预占 → Redis Stream → 数据库 Outbox → RocketMQ 的秒杀履约链路，补充唯一资格、重复消息、pending 接管、死信与精确补偿处理。
- 使用 Kafka 处理浏览及订单行为，按 eventId 去重后事务更新分钟桶，数据库提交后确认 offset；提供事件回执和 5/60 分钟热榜。

若引用性能数字，要附条件。历史 [cache-benchmark.json](../docs/cache-benchmark.json) 使用 10000 次/阶段、并发 8、预热 200、单实例与固定热点 `GET /shop/1`，基础版约 1655 QPS，缓存版约 2295 QPS，测量区间详情回源 10000 → 0。它不能写成“系统生产吞吐提升到某个通用值”或推导秒杀容量。

## 7. 重点追问与回答思路

**为什么 Redis 锁不能取代数据库唯一键？** 锁有租约和连接故障窗口，旧持有者可能继续执行。数据库事务、条件更新和唯一键负责最终事实约束。

**Lua 原子性是否让订单不会丢？** 它保护 Redis 内的入口操作，不能保证数据库履约完成。持久化、Stream ACK 时机、Outbox 交接和重试处理后续窗口；Redis 预占尚未登记就永久丢失时仍有恢复边界。

**为什么 Outbox 发完还要 Inbox？** 发送确认丢失可能重发；消费后 ACK 丢失可能重投。稳定 eventId 与消费组唯一登记让重复进入不会重复完成数据库效果。

**为什么不是 Exactly Once？** Kafka/RocketMQ 与 MySQL 没有共享原子事务，跨 Redis 与文件更没有。这里用至少一次与幂等组合取得指定效果，保证范围需要按业务副作用解释。

**为什么 Canal 不直接把每行新值写到缓存？** 旧日志追赶可能落后当前数据库，直接镜像会写回过期值。以失效为主，重建读取当前事实，并用版本防止旧加载污染。

**为什么浏览允许丢、订单不允许随便丢？** 两类数据对业务的影响不同。浏览统计选择不阻塞主请求，明确有界与丢弃指标；订单分析从持久任务出发可以重驱动。

**UV 为什么没有匿名用户？** 当前口径只识别登录 userId。未来匿名统计要设计访客标识、隐私、误差和去重周期，不能把 PV 当 UV。

**为什么 Feed 下一页还带 offset？** score 时间戳可能相同，只用 minTime 会重读或跳过同分项；要传回并在同一 score 上累计偏移。

**订单价格为什么不实时查券价？** 用户创建时确认的价格应固定；订单快照避免商品后来改价影响历史订单和付款验证。

**页面为什么没有一键停 Kafka 测故障？** 普通体验需要保护共享业务，页面展示实际观察；破坏性故障在隔离环境复现，用测试报告说明边界。

## 8. 从请求解释一条完整故障链

以“用户抢到了资格，RocketMQ 暂时停机”为例：Lua 已预占并写 Stream，返回 PROCESSING；消费者登记预约并持久写 Outbox，ACK Stream；发送者失败退避，任务保留；MQ 恢复后使用原 eventId 重投；消费者依据预约履约，数据库条件扣库存并保存订单；用户查询变为 SUCCESS。

若自动尝试达到边界，任务/预约进入 REVIEW，管理员需要复核后重试或明确失败补偿。不能在 Broker 短时故障就立即归还预占，同时保留原履约任务。

按这个顺序讲，面试官能看到你理解“哪里是事实、哪里能重试、何时 ACK、谁来恢复”。

## 9. 练习题：先独立回答，再核对

<a id="section-09-01"></a>

### 题一：热点店铺连续查三次，数据库是否必须查三次？

先列出假设：服务刚启动还是已预热；缓存是否启用；查询是否来自同一 HTTP 请求；是否刚发生失效。缺少这些条件，无法给出唯一次数。

在一次体验缓存请求中连续读取相同店铺，第二次应有 request-scope 命中；第一次可能来自 Caffeine、Memcache、Redis 或数据库。换一次 HTTP 请求，请求内缓存必须清空；仍可能命中其他层。不能把请求内命中理解成用户浏览器保存了数据库查询结果。

检查点：能从 trace 找到真实路径，并说明缓存热读不会必然出现 MySQL 路径。

<a id="section-09-02"></a>

### 题二：Outbox 已经 SENT，为什么还可能需要重驱动？

SENT 说明发送者已收到投递成功确认，不说明消费者已完成指定业务。消费侧故障、任务长时间未处理，仍需要观察 Inbox 与 DONE。定时事件在到期前等待属于正常行为，不能直接按普通即时任务处理。

检查点：同时查看发送与消费证据，说明稳定 eventId 如何让重投不重复执行数据库效果。

<a id="section-09-03"></a>

### 题三：同一个普通券连续点领取按钮，应生成两张有效订单吗？

当前方案对用户与券组合使用稳定数据库槽位并加锁；事务内检查已有有效订单，同一有效领取返回原订单。不要把重复请求的成功响应次数当成新增订单数。取消后再次领取属于另一条业务路径，需要区分订单状态和资格规则。

检查点：两次返回的订单 ID、本人订单事实、普通订单槽位的作用都能解释。

<a id="section-09-04"></a>

### 题四：网页提交 3 条浏览事件，为什么热榜不一定立即增加 3？

浏览是有界尽力采集；后台发送、Kafka 消费、数据库事务、热榜刷新之间都有时间差。先查三个 eventId 的持久回执。若未持久化，不能要求热榜计算它们；若都已持久化，再核对窗口、店铺与缓存刷新，不以立即点击时的热榜变化判断整条链路是否正确。

检查点：区分提交成功与 PERSISTED，指出匿名用户只影响 PV，不增加当前登录 UV。

<a id="section-09-05"></a>

### 题五：现在还能补哪些真实缺口？

优先从现有业务闭环中选，而不急着加新组件。当前秒杀履约的 `createVoucherOrder` 尚未完整接入普通订单使用的 `lifecycle.created` 事件路径，不能承诺所有秒杀都自动计入 ORDER_CREATED 分析。订单表保存店铺快照，但部分查询展示仍依赖当前券关联，也值得补齐历史展示约束。

这些是读源码可以定位的改进题。练习时先描述失败或遗漏例子，再提出需要修改的 Service、事务位置、Mapper 与测试。文档说明缺口并不意味着本次已经实现它们。

<a id="section-10"></a>

## 10. 如何把演示结果变成可信的项目证据

一份好的证据至少说明“测了什么、怎样测、得到什么、不能推出什么”。以缓存历史报告为例：

| 问题 | 报告给出的条件或结论 |
| --- | --- |
| 测什么 | 固定 GET /shop/1 的热点查询 |
| 测量条件 | 单 Java 实例，并发 8，预热 200，每阶段 10000 请求 |
| 观察指标 | QPS、P50/P95/P99、错误数、店铺详情回源数 |
| 可以说什么 | 这组测量条件下，缓存方案减少详情回源并改善耗时与吞吐 |
| 不能推什么 | 全站容量、秒杀每秒吞吐、多机高可用、所有接口同样收益 |

“提升了约多少百分比”也要统一口径：`(优化值-基线值)/基线值` 用于吞吐增幅；延迟下降则用 `(基线值-优化值)/基线值`。不把 QPS、时间、错误率混成同一个“性能提升”。如果自己复测，保存新的环境和日期，不直接覆盖旧报告的数据。

对于可靠性，证据应是具体断言：“同 eventId 重放后计数保持不变”“CDC 处理失败不 ACK”“别人不能查看本人订单进度”。只写“消息可靠、接口安全”没有说明检查对象。

<a id="section-13"></a>

## 13. 把教程变成能独立讲解的学习训练

<a id="section-13-01"></a>

### 第一轮只追通一条链，不要求一次背完

先选择店铺查询，跟到 Controller、Service、CacheClient 和 Mapper，保存一次真实响应与采样。然后选普通订单，找到订单事实、创建 Outbox 和事件历史。第三步才看秒杀，把准入、预约和履约分开。最后进入 Kafka 与 CDC，分别回答“分析为什么异步”与“数据库直改如何传播”。

这是一条由短到长的学习路线。初学者先通过短链路理解输入输出和分层，再用同样的问题读长链路。阅读卡住时，退回到当前方法的输入、返回和下一位责任人，而不是跳到另一个中间件教程重新开始。

| 阶段 | 必须完成的操作 | 应留下的成果 | 没有完成时继续查哪里 |
| --- | --- | --- | --- |
| 启动与查询 | 分类、店铺、代理查询 | 环境记录和一条响应 | 启动日志、URL、运行开关 |
| 登录与普通订单 | 登录、领券、重复领券、本人查询 | 同一用户与订单 ID 的链路图 | 请求头、归属校验、槽位事务 |
| 缓存与失效 | 采样两次读并解释路径 | 版本/owner 的失败时序 | CacheClient、脚本与并发测试 |
| 秒杀与 MQ | 追踪原预约到订单 | 每段持久责任与状态表 | Stream、预约、Outbox、履约 |
| Kafka 与 CDC | 查回执、解释桶与更新传播 | 指标演算和变更证据 | 事实表、窗口、检查点、过滤 |

这些阶段按完成标准推进，比规定“某一天必须读完几百行代码”更适合不同基础的人。学习记录可以多次修订，但每一轮增加一份新的可验证产物。

<a id="section-13-02"></a>

### 缓存亮点的一段回答，怎样拆成四层

第一层讲问题：“热门店铺查询集中回源会压数据库，更新时还可能有旧加载晚到。”第二层讲方案：“读取用多层副本减少成本，重建用进程内合并与 Redis owner 锁，失效推进版本。”第三层讲失败：“数据库已更新后，旧查询携带旧版本，Lua 会拒绝它写回。”第四层讲证据和边界：“并发测试控制这个窗口；页面能观察读路径，短副本和通知仍使系统有最终一致性窗口。”

如果只讲第一层，会像泛泛介绍缓存；只讲第二层，会像罗列术语；讲到第三层能说明你理解实现；加第四层则能避免把一个通过的测试扩大成所有场景都强一致。

追问 Memcache 是不是必须，可以说明它提供共享短副本，也增加组件与网络开销，是否保留要由真实流量和收益决定。当前项目实现这个层次，不等于任何系统都必须用同样五层。

<a id="section-13-03"></a>

### 可靠消息的一段回答，怎样承受继续追问

先讲“订单与待发送事件同事务”，再解释“Relay 短事务领取，提交后发送”；随后讲“确认丢失沿原 eventId 重发，消费身份与数据库效果同事务去重”。面试官问为什么有 SENT 后还重驱动，就说明发送确认不证明消费完成，超过观察窗口还要检查持久进度。

再问 exactly-once 时，区分传输和业务效果：传输可能至少一次，数据库步骤靠幂等收敛，Redis 和文件等外部效果另需安全重放。再问数据库与 MQ 为何不一起回滚，说明它们不在同一个本地 SQL 事务。这条追问链能检验你是否真的理解边界，而不是记住 Outbox 这个词。

<a id="section-13-04"></a>

### 六个练习题与完整核对思路

**题一：没有拿到缓存锁的线程，能不能为了更快直接查库？**

当前互斥重建策略下不能绕过锁直接回源，否则多个等待者都会击穿到数据库。应等待、重新检查缓存，并在等待上限后按当前契约失败。是否允许额外回源属于另一种负载和可用性策略，不应偷偷更改原机制。

**题二：收到 ORDER_EXPIRE，订单现在已支付，应该怎么处理？**

重新读取锁定订单的当前事实，发现不再待支付就不关闭。消息触发检查，不决定当前事实。事件迟到与重复都不能把已支付覆盖为关闭。

**题三：同一个 eventId 改了 shopId 再发，为什么不能按重复成功处理？**

唯一键只告诉你身份已存在，不能告诉你内容合法一致。比较已存内容发现店铺不同后应拒绝，避免污染另一家店的统计，也避免把生产端身份生成错误隐藏起来。

**题四：数据库剩余 10，Redis 剩余 8，是否立即加回 2？**

先查未完成准入与预约，可能正有两人等待履约。立即补库存会重复开放资格。只有明确定位原责任、状态和活动基线后才能按恢复流程操作，读对账报告不等于执行修复。

**题五：关注 Feed 的首批任务 DONE，是否所有粉丝已收到？**

未必。满批次可能持久登记续传任务；DONE 表示这一批处理完成。继续沿笔记与后续任务查游标，确认最后一批结束；还要考虑当前 Feed 容量截断。

**题六：所有容器 Up，是否可以把“全功能已验证”写进简历？**

不能。容器状态只证明进程状态，需要正常业务、身份归属、重复与故障断言分别提供证据。报告必须注明版本、环境和实际执行过的用例；历史结果不能当当前运行结论。

<a id="section-13-05"></a>

### 选择一次真正能完成的改进，而不是堆新组件

候选方向可以是秒杀统一生命周期与分析口径、真实短信、真实支付闭环、历史数据清理或更细的观测。选择前写清：现在缺什么，用户会遇到什么，修改哪些事实或状态，如何保留旧协议，怎样验证正常和失败路径。

例如秒杀统一事件不能只在任意位置追加 ORDER_CREATED：要确定订单成功落库的事务边界，重复履约是否重复登记，已有状态和截止逻辑是否适用于秒杀，以及分析是否沿原身份去重。能完成这一闭环，比同时写上三个尚未验证的新组件更有面试价值。

<a id="section-13-06"></a>

### 一份简历条目写完后，自己逐句核对

对每句“保证”“提升”“支持”，分别追问它的范围。保证哪个不变量？提升用什么基线、多少负载和什么环境？支持的是正常请求、重复请求还是崩溃恢复？找到对应代码、测试或实验记录，找不到则缩小表述。

练习讲解时可以让同学随机选一个失败位置，你沿同一业务 ID 解释恢复。不要把历史报告的吞吐数字背成通用性能承诺，也不要把尚未接入的退款、核销和支付写进已经完成的功能清单。
