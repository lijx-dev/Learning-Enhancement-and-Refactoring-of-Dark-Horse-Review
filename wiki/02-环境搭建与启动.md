## 1. 推荐从 Docker 完整环境开始

Docker 可以把 MySQL、Redis、消息队列和 Java 的运行环境打包管理。使用这条路线，不必先在电脑上逐个安装数据库和消息队列；但必须先安装并启动支持 Compose v2 的 Docker 环境，且可以获取本项目使用的镜像和 Maven 依赖。

终端是输入命令的地方。先进入 Java 项目，而不是停在外层“黑马点评”目录：

```bash
cd '/path/to/Learning-Enhancement-and-Refactoring-of-Dark-Horse-Review'
docker version
docker compose version
```

换了一台电脑时，把 `cd` 的路径替换成实际下载位置。路径有中文或空格时保留引号。

完整环境包含多个 JVM 与数据库进程，需要给 Docker 留出足够内存。首次启动可能经历镜像下载、数据库初始化、Topic 创建和 Maven 下载，不能只凭页面暂时打不开就判断代码有问题。

## 2. 一次启动完整环境

```bash
docker compose -f dev/docker-compose.yml up -d
docker compose -f dev/docker-compose.yml ps -a
docker compose -f dev/docker-compose.yml logs -f java
```

`up` 表示创建或启动服务，`-d` 表示后台运行。日志出现 Spring Boot 启动完成，且 Java 健康检查通过后，可以按 `Ctrl+C` 退出日志跟随；这不会停止后台服务。

| 地址 | 用途 |
| --- | --- |
| [http://127.0.0.1:8080/](http://127.0.0.1:8080/) | 桌面首页 |
| [http://127.0.0.1:8080/experience.html](http://127.0.0.1:8080/experience.html) | 三步体验验证 |
| `http://127.0.0.1:8081/actuator/health` | Java 基础健康检查 |
| `http://127.0.0.1:8081/shop-type/list` | 直接查询 Java 的分类接口 |

MySQL、Redis、Canal、Memcache、RocketMQ 和 Kafka 默认仅在 Compose 内网开放。Kafka 的 `kafka:9092` 是容器间地址，不能直接拿来配置宿主机上的 IDE。

某些初始化容器，例如 `mq-init`、`kafka-init`、数据目录初始化任务，正常执行后会 `Exited (0)`。它们并不是需要一直运行的服务器。应重点看 Java、web、数据库和消息服务的状态，遇到非零退出再检查对应日志。

## 3. 看懂启动过程，而不只是照抄命令

<a id="section-03-01"></a>

### docker compose 命令如何拆开读

`docker` 调用容器引擎，`compose` 按配置管理多服务，`-f dev/docker-compose.yml` 指定本项目配置，`up` 创建/启动，`-d` 放到后台。命令执行成功只是说明启动指令已提交，不是 Java 已经完成初始化。

Compose 服务名就是日志和管理时使用的名字：`java` 是后端，`web` 是页面，`mysql` 是数据库。它们与容器 ID 不同；通常不用复制长容器 ID 才能排查。

```bash
# 看所有服务，包括完成后退出的初始化任务
docker compose -f dev/docker-compose.yml ps -a
# 只看 Java 最近日志，而不是一次输出全项目日志
docker compose -f dev/docker-compose.yml logs --tail=80 java
# 验证 Java 已经能响应公开接口
curl -i 'http://127.0.0.1:8081/shop-type/list'
# 验证 Nginx 的 /api 代理访问同一接口
curl -i 'http://127.0.0.1:8080/api/shop-type/list'
```

最后两个请求应访问同一业务。8081 正常但 8080 的 `/api` 失败，重点看 Nginx；二者都失败，先看 Java 与依赖。不要一看到网页错误就立即改前端代码。

<a id="section-03-02"></a>

### 实际启动会经过哪些步骤

| 阶段 | 正在做什么 | 等待时看什么 |
| --- | --- | --- |
| 获取镜像 | 下载 Maven、MySQL、Redis、MQ 等镜像 | Compose 输出与网络 |
| 初始化数据目录 | 建立数据库、日志目录与权限 | 对应 init 服务退出码 |
| 依赖启动 | MySQL/Redis/Canal/Broker 接受连接 | 健康状态与各自日志 |
| 初始化 Topic | 创建明确命名的消息 Topic | mq-init/kafka-init 是否成功 |
| Maven 启动 | 获取依赖、编译代码 | Java 容器日志 |
| Flyway | 对数据库执行未执行的迁移 | 迁移版本、失败 SQL |
| Spring 初始化 | 建立 Bean、消费者、定时任务 | Started 日志和接口响应 |

因此第一次运行比后续慢很常见。重复运行 up 一般复用已有卷和依赖；删除所有卷会重新初始化，但也会丢掉已有数据。

<a id="section-03-03"></a>

### 127.0.0.1、java、mysql 分别是谁

在宿主机浏览器里，127.0.0.1 指你的电脑。在 Java 容器内部，127.0.0.1 指 Java 容器自己，不是 MySQL 容器。容器间通过 Compose 服务名，例如 mysql、redis、kafka 连接。

这解释了常见错误：把宿主机数据库地址原样写进容器配置，或把容器名 kafka 原样写进 IDE。地址是否正确取决于发起连接的进程在哪个网络环境。

<a id="section-03-04"></a>

### 数据卷、源码挂载和依赖缓存不是同一东西

数据卷保存 MySQL、Redis、Broker 的数据；源码挂载使容器看到当前 Java/前端文件；Maven 缓存卷保存下载过的依赖。重启 Java 不会把数据库初始化一遍，也不一定能改变已经创建的容器环境变量。

检查配置变更是否生效时，先判断改的是源码、环境变量还是数据库结构：源码需要重新编译运行，环境变量需要重建服务，结构变更通过新迁移执行。三种情况不能都用浏览器刷新来解决。

<a id="section-03-05"></a>

### 一份能照做的首次验收记录

| 次序 | 操作 | 达标结果 | 不达标的下一步 |
| --- | --- | --- | --- |
| 1 | ps -a | 核心服务运行，init 为退出 0 | 查失败服务日志 |
| 2 | 直接查询分类 | success=true、有演示分类 | 查 Java/数据库 |
| 3 | 经 /api 查询分类 | 同样得到分类 | 查 Nginx 代理 |
| 4 | 打开首页店铺 | 名称、价格与数据加载正常 | 看浏览器 Network 响应 |
| 5 | 正常登录 | 获取 token，能查 me | 按验证码与请求头排查 |
| 6 | 打开体验页 | 能力状态有采样，缓存有路径 | 按扩展开关排查 |
| 7 | 提交浏览事件 | 这批 eventId 有持久回执 | 查 Kafka 消费与统计 |

有些健康状态只证明进程可响应，最后两步是在验证真实工作链路。部署完成应同时有进程状态和业务证据。

## 4. 数据从哪里来

[Compose 文件](../dev/docker-compose.yml) 在空 MySQL 数据卷首次初始化时导入 [原始建表与演示数据](../src/main/resources/db/hmdp.sql)，再启动 Java。Java 启动时由 Flyway 执行 V1～V9 增量迁移，创建预约、消息、媒体和行为分析等表。

“初始化 SQL”与“迁移 SQL”职责不同：初始化脚本只在新数据卷第一次执行；Flyway 根据版本记录决定哪些迁移尚未执行。已有 MySQL 卷时修改初始化 SQL，不会自动重新导入。不要为了重新执行脚本直接删业务卷，也不要修改已在别人环境执行过的迁移内容；新增变更应使用新的版本文件。

## 5. 第一次登录

1. 打开网页登录入口，输入自己的演示手机号并点击获取验证码。
2. 在 Java 服务日志中找到刚产生的六位验证码。
3. 在两分钟内输入验证码提交登录。
4. 页面保存令牌后，即可进入个人中心、签到、领券和订单等页面。

```bash
docker compose -f dev/docker-compose.yml logs --tail=100 java
```

当前没有真实短信发送，日志中的“发送短信验证码成功”不表示手机会收到短信。验证码只允许成功消费一次；重复使用、输错或过期都会失败。相同手机号一分钟只能获取一次，并有登录尝试限流。多人同时操作时，日志中的验证码没有绑定手机号显示，建议演示时按账号分批操作。

浏览器业务令牌放在 `sessionStorage.token`，随 `authorization` 请求头发送。令牌可以访问本人数据，应像密码一样保管。不同标签页的 sessionStorage 不完全等同于共享 Cookie；遇到新标签页未登录，先在该标签页登录。

## 6. 怎样设置商品管理与运维权限

普通注册用户不会自动成为管理员。管理员是配置中明确列出的用户 ID。先正常登录，再用开发者工具查看 `GET /user/me` 的 `data.id`，然后在启动 Java 时设置：

```bash
export HMDP_ADMIN_IDS='你的用户ID'
docker compose -f dev/docker-compose.yml up -d --no-deps java
```

多个 ID 用英文逗号分隔。示例中的文字必须替换为实际数字。`export` 在当前终端会话中有效；后续所有 Compose 命令应在同一环境配置下执行，也可以用项目根目录未提交的 `.env` 固定配置。不要把登录令牌、数据库密码或真实监控密钥写进分享文档。

管理员可以准备演示普通券与秒杀活动、查询运维任务并执行受控恢复。监控 Bearer 凭证只用于读取 Prometheus 指标，不赋予业务管理员权限。

当前部分 Spring 配置项仍使用 `citylens.*` 历史前缀；Compose 已用 `HMDP_ADMIN_IDS` 等变量进行桥接。这只是配置名的兼容，不需要启动其他项目。

## 7. 开关和端口

本地完整 Compose 默认打开体验、CDC、Memcache、RocketMQ、秒杀 MQ 交接和 Kafka。单独启动 Java 时，很多扩展默认关闭，见附录配置表。

```bash
# 当前终端持续使用这些端口，后续 Compose 命令也沿用
export HMDP_WEB_PORT=8088
export HMDP_API_PORT=8089
docker compose -f dev/docker-compose.yml up -d
```

然后页面改成 `http://127.0.0.1:8088/`，Java 改成 8089。不要在下次启动时忘记这些变量，否则 Compose 会尝试恢复默认端口。

关闭体验接口：

```bash
export HMDP_EXPERIENCE_ENABLED=false
docker compose -f dev/docker-compose.yml up -d --no-deps java
```

环境变量变化需要重新创建 Java 服务，单纯 `restart` 不会刷新容器配置。源码修改后可重启 Java，让 Maven 重新启动编译；前端静态文件有目录挂载，通常刷新浏览器即可看到。

## 8. 停止、重启与日志

```bash
# 只重启 Java；已有数据保留
docker compose -f dev/docker-compose.yml restart java
# 查看最近的服务日志
docker compose -f dev/docker-compose.yml logs --tail=100 java canal rocketmq kafka
# 停止整套开发环境并保留数据卷
docker compose -f dev/docker-compose.yml down
# 下次继续使用已有数据
docker compose -f dev/docker-compose.yml up -d
```

日常停止不要加 `-v`。`down -v` 会删除当前 Compose 项目管理的数据卷，不适合保存了业务数据的环境。第 13 章仅在明确的隔离测试项目中使用它清理临时数据。

## 9. 可选监控

```bash
docker compose -f dev/docker-compose.yml --profile monitoring up -d
```

默认 Prometheus 访问 `http://127.0.0.1:9091/`，Alertmanager 访问 `http://127.0.0.1:9094/`。监控抓取凭证与 Java `HMDP_MONITOR_TOKEN` 应一致；本地默认值仅用于开发。已配置告警规则，但没有接入真实邮件、短信或聊天通知通道。

## 10. 在 IDE 中单独启动 Java

这条路线适合想打断点的同学。先准备 JDK 8、Maven、MySQL 和 Redis；导入 `hmdp.sql` 后，覆盖默认课程地址：

```bash
export SPRING_DATASOURCE_URL='jdbc:mysql://127.0.0.1:3306/hmdp?useSSL=false&serverTimezone=UTC&characterEncoding=utf8'
export SPRING_DATASOURCE_USERNAME='root'
export SPRING_DATASOURCE_PASSWORD='<你的本地数据库密码>'
export SPRING_REDIS_HOST='127.0.0.1'
export SPRING_REDIS_PORT='6379'
export SPRING_REDIS_PASSWORD=''
mvn spring-boot:run
```

Redis 有密码时填实际密码。IDE 运行配置中也可以设置同名环境变量。数据库和 Redis 密码默认不再内置课程值，分别由 `SPRING_DATASOURCE_PASSWORD`、`SPRING_REDIS_PASSWORD` 提供。独立 Java 的图片目录默认为项目下 `./data/uploads/`，也可设置 `HMDP_UPLOAD_DIR` 为可写目录；独立部署 Nginx 时须将 `/imgs` 指向同一目录。Compose 则自动使用命名卷 `uploads`。缺失的历史本地图片显示占位图，无需额外下载旧 Nginx 目录。主类为 [HmDianPingApplication](../src/main/java/com/hmdp/HmDianPingApplication.java)。Spring 会继续执行增量迁移。

单独 Maven 只启动 Java，不会启动前端 Nginx，也不会自动配置 Canal、Kafka 和 RocketMQ。若要 IDE 调试完整消息链路，需要另行暴露并配置相应依赖地址，包括 Kafka 对外 advertised listeners；只把 `kafka:9092` 改成 `localhost:9092` 通常不够。初学者先用完整 Compose 验证，再逐步搭建这一环境。

## 11. 给别人体验时如何交付

附上这份 Wiki、源码、启动命令与体验验证页链接，并说明验证码从部署者的 Java 日志获取。独立下载运行的人可查看自己的日志；访问你部署的共享环境的人需要你提供可正常登录的测试方式，或者接入短信服务。

当前发布端口绑定 `127.0.0.1`，别人无法通过你的局域网 IP 直接访问。共享部署时需要显式配置网络入口、反向代理、HTTPS 和访问控制，再使用可访问的真实域名。发 `127.0.0.1` 给别人会访问对方自己的电脑。

先验收：首页能显示真实分类和店铺；登录后能查看本人资料；体验页缓存读取得到记录；Kafka 事件有匹配回执。只看到静态页面并不足以证明所有后端依赖工作正常。

## 12. 把第一次启动变成可重复的操作教程

<a id="section-12-01"></a>

### 开始前检查什么，检查结果怎么读

先确认终端位于 Java 项目根目录，里面应同时能找到 `pom.xml`、`dev/docker-compose.yml` 和 `frontend`。如果位于上一级“点评”，相同的相对路径会指向不存在的文件。命令找不到配置时，先检查位置，别急着重新下载项目。

```bash
pwd
ls pom.xml dev/docker-compose.yml frontend/index.html
docker version
docker compose version
```

`docker version` 有 Client 不代表引擎已可用，还需要能读取 Server 信息。在 macOS 上 Docker Desktop 没启动时，常见现象是客户端版本能显示，但连接 daemon 失败。等 Docker 引擎可用再执行 Compose。当前环境要同时运行多个 Java 中间件；若机器资源不足，启动慢与被系统终止应从容器日志和资源状态区分，不能承诺所有电脑都有同样的启动时间。

Compose 的首次运行包括下载镜像、初始化持久卷和下载 Maven 依赖。后续使用同一套数据卷和 Maven 缓存，过程通常不同。写验收记录时区分“首次启动”和“已有依赖的重启”，两者时间不能直接比较。

<a id="section-12-02"></a>

### 用三层检查定位问题，别只看首页

第一层检查容器。执行 `ps -a` 看依赖有没有反复退出；Kafka 和 MQ 初始化任务退出码 0 是任务完成，不能只凭 Exited 判断失败。Java 容器 Up 也可能仍在下载依赖或启动 Spring。

第二层检查 Java。读取 Java 最近日志，确认是否编译失败、数据库连接失败或迁移失败，再请求 health 和分类。health 说明健康入口可用，分类返回真实数组说明至少数据库查询链路已经可用；这仍不等于 Kafka 已完成消费。

第三层检查 Nginx。先测试 `/api/shop-type/list`，再打开首页。直连 Java 成功而代理失败，优先检查 Nginx 转发和上游地址；代理成功而页面空白，优先检查浏览器资源、控制台和响应解析。这样每次只缩小一个问题范围。

```bash
docker compose -f dev/docker-compose.yml ps -a
docker compose -f dev/docker-compose.yml logs --tail=80 java
curl -i 'http://127.0.0.1:8081/shop-type/list'
curl -i 'http://127.0.0.1:8080/api/shop-type/list'
```

不要期待两个 curl 都返回完全相同的 HTTP 头。要比较的是是否有业务 JSON、是否成功以及真实数据是否一致。如果得到 HTML，应检查是否请求了页面路径，或者代理路径没有命中。

<a id="section-12-03"></a>

### 哪类修改需要哪一种启动动作

| 修改内容 | 推荐动作 | 原因 |
| --- | --- | --- |
| `frontend` 下已挂载的静态文件 | 刷新页面；必要时检查浏览器缓存 | 文件来自目录挂载，不需要重新构建 Java |
| Java 源码 | 重启 Java，查看重新编译和 Spring 启动日志 | 当前容器运行 `spring-boot:run`，不是自动热部署承诺 |
| Compose 注入的环境变量 | 同一配置下执行 `up -d --no-deps java` | 要重新创建容器以改变环境，restart 沿用旧环境 |
| MySQL 初始化 SQL | 先判断数据卷是否已经初始化 | 首次初始化脚本不会因文件修改自动在旧库重跑 |
| 新的 Flyway 迁移 | 重启 Java，检查迁移记录 | Spring 启动时应用尚未执行的版本迁移 |

已执行的迁移不要靠改旧文件来升级，否则可能出现校验和不匹配。当前教程的读取练习使用已有迁移；真正新增数据库结构时应新建后续版本，让所有人从旧库升级时经历同一变化。

<a id="section-12-04"></a>

### 数据还在，但页面登录丢了，为什么不矛盾

MySQL 的订单和用户在数据库卷中；登录令牌在 Redis，浏览器还要保留对应 token。三个位置分别保存不同内容。换一个浏览器或标签页后，用户表仍在，不代表该页面自动具有登录身份。

再看文件上传：数据库保存资源记录与引用关系，实际图片文件来自挂载目录。只备份数据库可能无法恢复图片；只拷贝图片也无法恢复归属和引用。交付源码的人与备份业务数据的人要准备的东西不一样，恢复时应同时核对数据卷、文件目录与配置。

<a id="section-12-05"></a>

### 登录与权限的一次完整验收

用普通账号登录，调用 `/user/me` 记录真实用户 ID。先验证本人签到、个人信息和订单；再尝试管理入口，普通账号被拒绝是权限验收的一部分。随后按前文把该 ID 加入管理员配置，重新创建 Java，重新请求管理功能。不能仅因管理按钮在页面显示，就认为后端允许执行。

监控令牌又是另一类凭证。Prometheus 使用 `Authorization: Bearer ...`；业务接口使用登录返回的原始 token。复制监控凭证到普通订单接口不会变成业务管理员。
