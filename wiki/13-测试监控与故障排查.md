## 2. 先建立验证层次：每种测试回答不同的问题

《Redis实战篇》经常先展示现象，再分析原因。工程测试也应该先写明期待的业务结果，再挑能验证它的手段。不要因为日志里出现“发送成功”，就结束对完整业务的判断。

| 验证层次 | 使用的对象 | 能回答的问题 | 单独不能回答的问题 |
| --- | --- | --- | --- |
| 静态分层/风格检查 | Java 源文件、规则 | 是否遵循 Mapper 分层、是否符合格式约定 | 真实事务是否成功，MQ 是否消费 |
| 单元测试 | 一个类与 mock 依赖 | 特定分支会调用什么、是否提前 ACK、是否误释放锁 | 真实 Redis、Canal、Broker 的网络行为 |
| 集成测试 | Spring 与隔离基础设施 | SQL 唯一约束、脚本、多层缓存、真实发送消费 | 长期容量、故障切换与所有生产配置 |
| HTTP/页面测试 | 实际接口和浏览器 | 参数、身份、响应、观察链路是否贯通 | 所有崩溃窗口是否可恢复 |
| 专门故障/性能实验 | 明确负载或故障注入 | 指定条件下的恢复行为、吞吐与尾延迟 | 任何其他规模和所有故障都正确 |

例如“旧缓存回填被拒绝”需要准确控制并发先后；页面随机点几下无法稳定产生这个窗口。相反，“其他用户不能查看订单进度”需要真实 HTTP 身份与归属校验，只 mock 一个 Mapper 返回值也不能替代。

<a id="section-02-01"></a>

### 写下预期不变量，再决定怎样测试

不变量是操作前后始终应成立的规则，初学时可理解为“无论重试几次也不能被破坏的底线”。本项目可按下面几条阅读测试：

- 未得到缓存锁的查询不调用回源函数，也不释放别人持有的锁。
- 在途加载经历版本失效后，旧结果不能污染新版本缓存。
- CDC 批次的处理或检查点保存失败时，不确认该批次。
- 同一个行为事件重放不能再次增加统计，同 ID 内容冲突不能伪装成合法重复。
- 本人订单接口必须依据登录身份检查归属，不能只凭订单号给别人查看。
- 对已经履约成功的订单，旧失败消息不能随便归还资格或库存。

每条规则都可以对应一个测试名字和一组断言。这样读测试时关注的是设计为什么成立，而不是只看绿色的数量。

## 5. 测试源码导读一：没有拿到锁，必须没有副作用

假设另一个请求正在持有缓存锁。本请求等到边界也没拿到锁，如果错误地执行 unlock，就可能释放别人的保护。测试要同时检查两件事：没有查数据库，没有动别人的锁。

以下为 [CacheConcurrencyTest.java](../src/test/java/com/hmdp/reliability/CacheConcurrencyTest.java) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```java
void failedLockAcquisitionDoesNotUnlockSomeoneElse() {
  StringRedisTemplate redis = mock(StringRedisTemplate.class);
  ValueOperations<String, String> values = mock(ValueOperations.class);
  when(redis.opsForValue()).thenReturn(values);
  when(values.setIfAbsent(anyString(), anyString(), eq(10L), eq(TimeUnit.SECONDS)))
      .thenReturn(false);
  CacheClient cache = new CacheClient(redis);
  AtomicInteger loads = new AtomicInteger();
  try {
    assertThrows(
        IllegalStateException.class,
        () ->
            cache.queryWithMutex(
                "test:",
                1L,
                String.class,
                id -> {
                  loads.incrementAndGet();
                  return "value";
                },
                1L,
                TimeUnit.MINUTES));
    assertEquals(0, loads.get());
    verify(redis, never()).delete(anyString());
    verify(redis, never()).execute(any(RedisScript.class), anyList(), any(Object[].class));
  } finally {
    cache.close();
  }
}
```


按准备、执行、断言三段来读：

1. mock 的 `setIfAbsent` 始终返回 false，模拟本请求始终拿不到锁。这里没有启动真实 Redis，所以这是一个分支行为测试。
2. 用 `AtomicInteger` 记录回源函数执行次数；预期 `queryWithMutex` 在等待边界抛出异常。
3. `loads=0` 说明没有绕过锁直接查库。两个 `never()` 分别检查没有 DEL，也没有通过 Lua 执行解锁或回填。
4. `finally` 关闭客户端内部资源，避免测试结束后线程残留。

这个测试只证明“拿不到锁的分支不会回源或误解锁”。旧版本回填、Memcache 和 Caffeine 的真实交互要看下面的集成测试，不能把所有缓存保证都归到这个测试名下。

## 6. 测试源码导读二：精确制造旧回填窗口

并发错误难复现，不能只依赖 `sleep` 运气。`CountDownLatch` 是一个可等待的信号：`began` 告诉测试旧加载已经开始，`finish` 让测试控制它什么时候继续。

以下为 [CacheLayersIntegrationTest.java](../src/test/java/com/hmdp/cache/CacheLayersIntegrationTest.java) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```java
void concurrentLoadingCoalescesAndInvalidatedFlightCannotPoisonNewGeneration() throws Exception {
  AtomicInteger loads = new AtomicInteger();
  ExecutorService pool = Executors.newFixedThreadPool(8);
  CountDownLatch began = new CountDownLatch(1);
  CountDownLatch finish = new CountDownLatch(1);

  try {
    List<Future<Shop>> reads = new ArrayList<>();
    for (int i = 0; i < 16; i++) {
      reads.add(
          pool.submit(
              () ->
                  cache.queryWithMutex(
                      prefix,
                      1L,
                      Shop.class,
                      id -> {
                        loads.incrementAndGet();
                        try {
                          Thread.sleep(30);
                        } catch (InterruptedException e) {
                          throw new IllegalStateException(e);
                        }
                        return shop("old");
                      },
                      1L,
                      TimeUnit.MINUTES)));
    }
    for (Future<Shop> f : reads) {
      assertEquals("old", f.get(5, TimeUnit.SECONDS).getName());
    }
    assertEquals(1, loads.get());
    cache.invalidate(prefix + 1);
    Future<Shop> old =
        pool.submit(
            () ->
                cache.queryWithMutex(
                    prefix,
                    1L,
                    Shop.class,
                    id -> {
                      began.countDown();
                      try {
                        finish.await(5, TimeUnit.SECONDS);
                      } catch (InterruptedException e) {
                        throw new IllegalStateException(e);
                      }
                      return shop("old");
                    },
                    1L,
                    TimeUnit.MINUTES));
    assertTrue(began.await(3, TimeUnit.SECONDS));
    cache.invalidate(prefix + 1);
    finish.countDown();
    old.get(5, TimeUnit.SECONDS);
    assertNull(redis.opsForValue().get(prefix + 1));
    assertNull(shared.get(prefix + 1, redis.opsForValue().get(prefix + "1:version")));
    assertEquals("database", read(cache, loads).getName());
  } finally {
    finish.countDown();
    pool.shutdownNow();
  }
}
```


前半段提交 16 个查询，线程池同时最多运行 8 个。回源函数增加一次计数并短暂停顿，全部请求取得 old，最后 `loads=1` 说明这一轮同 Key 的加载被合并。16 是任务数，8 是工作线程数，不能直接改写成“16 个真实 HTTP 并发”。

后半段先失效，启动一轮新回源并等待 `began`。此时回源已经持有旧版本；主测试线程再次失效，然后用 `finish` 放行，让旧结果有机会尝试回填。这个次序就是人为构造：

```text
加载线程：读版本 → 开始回源 ─── 等待 ─── 返回 old → 尝试回填
测试线程：                收到 began → invalidate → finish 放行
预期：                                            旧回填被拒绝
```

`assertNull(redis...)` 验证旧加载没有重新写 Redis 数据；对 shared 的检查验证当前版本命名空间没有被污染。最后重新读取得 database，确认拒绝旧写没有把后续正确加载永久堵住。

注意，测试并没有断言旧加载线程绝对拿不到 old；它重点保护后续缓存状态。这与“失效一发生，所有已经在途的请求都立即读最新值”不是同一种保证。

## 7. 测试源码导读三：CDC 为什么失败不 ACK

假设 Canal 交来批次 10。投影成功，但还没有确认时出现失败，下次重放应仍能再次处理；如果提前 ACK，这个批次就可能被当作已经完成。

以下为 [CanalBatchTest.java](../src/test/java/com/hmdp/cache/CanalBatchTest.java) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```java
void checkpointAndAckFollowSuccessfulProjectionButFailureRollsBack() throws Exception {
  CacheChangeProjector projector = mock(CacheChangeProjector.class);
  ICacheCheckpointService checkpoint = mock(ICacheCheckpointService.class);
  CanalConnector connector = mock(CanalConnector.class);
  CanalCacheConsumer consumer =
      new CanalCacheConsumer(projector, mock(RedissonClient.class), new SimpleMeterRegistry());
  ReflectionTestUtils.setField(consumer, "cacheCheckpointService", checkpoint);
  ReflectionTestUtils.setField(consumer, "destination", "example");
  CanalEntry.Entry entry =
      CanalEntry.Entry.newBuilder()
          .setHeader(
              CanalEntry.Header.newBuilder().setLogfileName("mysql-bin.1").setLogfileOffset(100))
          .build();
  when(projector.isRelevantEntry(entry)).thenReturn(true);
  Message message = new Message(10, Collections.singletonList(entry));
  consumer.processBatch(connector, message);
  InOrder order = inOrder(projector, checkpoint, connector);
  order.verify(projector).projectEntryChanges(entry);
  order
      .verify(checkpoint)
      .saveCheckpoint(anyString(), anyLong(), anyString(), anyLong(), anyLong());
  order.verify(connector).ack(10);
  reset(projector, checkpoint, connector);
  doThrow(new IllegalStateException("Redis unavailable"))
      .when(projector)
      .projectEntryChanges(entry);
  assertThrows(IllegalStateException.class, () -> consumer.processBatch(connector, message));
  verify(connector).rollback(10);
  verify(connector, never()).ack(anyLong());
  verifyNoInteractions(checkpoint);
  consumer.stop();
}
```


`InOrder` 验证调用顺序是投影 → 检查点 → ACK。检查点不是启动恢复位点的全部来源，这里验证的是本项目的处理与审计顺序。

随后 `reset` 清理 mock 的先前记录与行为，`doThrow` 注入投影失败。第二段要求抛出异常、调用 `rollback(10)`、从不 ACK、也不写检查点。测试中的 rollback 是 Canal 批次回滚接口，不表示自动撤销此前已经发生的每项 Redis 副作用；所以投影还必须允许重放。

同一个文件另有检查点保存失败测试，以及仅包含不相关事务边界时不保存检查点的测试。后者防止检查点写入本身被订阅后形成无用反馈。真实 MySQL → binlog → Canal → Redis 的传播，则要结合 `CacheCdcIntegrationTest` 看，mock 批次测试不能替代它。

## 8. 测试源码导读四：手算统计，再看断言

```java
void windowUvDeduplicatesAcrossMinutesAndAnonymousVisitsOnlyAddPv() {
  long now = System.currentTimeMillis() / 60000 * 60000;
  aggregation.accept(event("visit-a", 100L, "VISIT", now));
  aggregation.accept(event("visit-b", 100L, "VISIT", now - 60000));
  aggregation.accept(event("visit-c", 101L, "VISIT", now));
  aggregation.accept(event("anonymous", null, "VISIT", now));
  aggregation.accept(event("order", 100L, "ORDER", now));
  aggregation.accept(event("payment", 100L, "PAID", now));
  Map<String, Object> rank = aggregation.ranking(5, 10).get(0);
  assertEquals(4, ((Number) rank.get("pv")).intValue());
  assertEquals(2, ((Number) rank.get("logged_uv")).intValue());
  assertEquals(1, ((Number) rank.get("orders")).intValue());
  assertEquals(1, ((Number) rank.get("mock_payments")).intValue());
  assertEquals(23, ((Number) rank.get("heat")).intValue());
}
```


在读最后五个断言之前，先独立计算：

| 输入 | 对 PV 的影响 | 对登录 UV 的影响 | 其他计数 |
| --- | --- | --- | --- |
| 用户 100 本分钟浏览 | +1 | 100 加入窗口集合 | 无 |
| 用户 100 前一分钟浏览 | +1 | 已在集合，不新增 | 无 |
| 用户 101 本分钟浏览 | +1 | 101 加入窗口集合 | 无 |
| 匿名本分钟浏览 | +1 | 不新增当前登录 UV | 无 |
| 用户 100 下单行为 | 不增加浏览 PV | 不作为浏览 UV | orders +1 |
| 用户 100 模拟付款行为 | 不增加浏览 PV | 不作为浏览 UV | mock_payments +1 |

所以 PV=4，登录 UV=2，订单=1，模拟付款=1，热度 `4+2×2+1×5+1×10=23`。同一个用户跨分钟去重是这项测试的关键。

这份测试直接调用聚合 Service，配置关闭后台分析消费，不经过真实 Kafka 传输。它的 fixture 会校验数据库名并清理隔离测试表；相关清理不属于业务 DAO 实现。真实 Kafka 的证据要看 Kafka 与 Experience 集成测试，不能根据本方法的六次 Service 调用就说“Broker 投递通过”。

## 9. HTTP 验证还需要身份、等待条件与清理边界

[ExperienceIntegrationTest](../src/test/java/com/hmdp/experience/ExperienceIntegrationTest.java) 把浏览提交与回执查询串起来，通过真实 Kafka 等待每个提交的 eventId 进入持久事实。等待有 30 秒上限，超时是失败，不会无限循环把问题隐藏掉。

同一类还检查匿名缓存观察、受保护接口，以及别人无法查看某个用户的订单进度。它创建隔离测试身份用于自动化；普通体验者按登录页正常登录，不照抄测试里构造 token 的方法到日常业务环境。

阅读时核对四点：测试数据库名保护是否生效；测试配置到底开启了哪个组件；断言查的是同一订单或事件 ID；等待成功的条件是否是持久事实。配置了 `DirtiesContext` 的测试还会让 Spring 上下文在完成后清理重建，防止后台消费者影响后续案例。

## 11. 性能数据怎样解释

历史 [缓存对比报告](../docs/cache-benchmark.json) 测一个 Java 实例、固定店铺热点、每阶段 10000 个 HTTP 请求、并发 8、预热 200，隔离 Docker MySQL 8/Redis 7/Memcache 1.6。

| 指标 | 直接回源基线 | 缓存优化 |
| --- | --- | --- |
| QPS | 约 1655 | 约 2295 |
| P50 | 3.255 ms | 2.171 ms |
| P95 | 13.546 ms | 10.686 ms |
| P99 | 24.072 ms | 20.971 ms |

## 12. 监控应看什么

启动 monitoring profile 后，Prometheus 根据 [prometheus.yml](../dev/monitoring/prometheus.yml) 抓取，告警规则在 [alerts.yml](../dev/monitoring/alerts.yml)。建议结合：

- API 请求量、错误率与延迟，先判断是否影响用户。
- 缓存层命中/回源/被栅栏拒绝的次数，判断查询压力来源。
- CDC 连接、事件延迟与最近检查点，判断缓存变更是否跟上。
- Stream lag/pending、预约 REVIEW，判断秒杀入口与交接。
- Outbox pending/inflight/review、MQ 发送/消费失败，判断可靠任务进度。
- Kafka consumer running、lag、浏览 dropped、分析 Outbox，判断统计延迟与丢弃。

Micrometer 源码里的点号名称输出到 Prometheus 时通常转为下划线，计数器还有 `_total` 等后缀。以 `/actuator/prometheus` 的实际输出和告警文件为准。

`/actuator/health` 返回 UP 是基础健康信号，不是 Canal、MQ、Kafka 的完整 readiness 证明。体验能力中 connected/clientStarted/consumerRunning 也只是采样状态，必须结合具体任务回执。

<a id="section-13"></a>

## 13. 从指标读到业务问题：不要只看一个绿色状态

<a id="section-13-01"></a>

### Counter、Gauge、Timer 分别是什么

Counter 是累计次数，通常一直递增。看它是否从 100 变成 101，只能说明又发生一次；判断当前问题强度要看一段时间内的增量或速率。Gauge 是此刻的数量，例如任务积压；Timer 则记录耗时分布。

下面直接解释当前 [alerts.yml](../dev/monitoring/alerts.yml) 中的规则，不要求读者先学完 PromQL：

| 规则中的表达 | 白话含义 | 后续去哪里找原因 |
| --- | --- | --- |
| `max(hmdp_outbox_pending) > 200` | 某实例看到待处理业务任务超过阈值 | `/ops/outbox`、发送错误与依赖状态 |
| `max(hmdp_outbox_review) > 0` | 有任务达到复核状态 | 精确任务 ID、kind、尝试原因 |
| `hmdp_kafka_consumer_running == 0` | 消费线程未处于运行状态 | Java 与 Kafka 日志、功能开关 |
| `max(hmdp_kafka_consumer_lag) > 1000` | 采样到未追上的行为消息超过阈值 | 消费速度、数据库、失败记录 |
| `rate(hmdp_kafka_visits_total{result="dropped"}[5m])` | 最近五分钟浏览丢弃的每秒速率 | 有界队列、发送异常与 Kafka |
| `hmdp_cdc_poll_age_seconds > 30` | 超过 30 秒没更新轮询时间 | CDC 线程与连接，不等同于某条业务日志延迟 |
| `histogram_quantile(0.95, ...)` | 用直方图估计最近窗口的 P95 | 对应 API 或事件处理的耗时来源 |
| `up{job="hmdp"} == 0` | Prometheus 无法抓到目标 | 接口进程、网络、监控凭证 |

规则还有 `for: 1m/2m` 等持续时间，意味着表达持续成立达到时长才触发。短暂抖动不一定马上告警；看不到告警也不代表完全没有抖动。阈值是当前演示配置，不应直接宣称适合所有生产负载。

<a id="section-13-02"></a>

### 三种“连接正常”仍然可能业务没完成

一是健康接口 UP，但某项后台消费没有开启。二是 Kafka 消费线程 running，却因数据库错误不断回放同一批。三是 RocketMQ 发送成功，但对应任务还没到期或消费尚未完成。

所以观察顺序应是用户结果 → 任务事实 → 组件指标 → 日志原因。浏览看匹配回执，订单看本人订单与任务状态，缓存看当前读取和失效证据。连接状态用于缩小范围，不能替代完成证据。

## 14. 初学者排障练习：网页有，接口为什么没有数据

第一步，在项目根目录查看容器状态：

```bash
docker compose -p hm-dianping -f dev/docker-compose.yml ps -a
```

找 web 和 java。`running` 表示容器进程还在，`healthy` 是配置的健康检查结果；都不能独自证明某个业务输入有效。容器刚启动时 Java 可能仍下载依赖或迁移数据库。

第二步，对比同一个公开接口的两个入口：

```bash
# 直接 Java
curl -i 'http://127.0.0.1:8081/shop-type/list'
# 经网页代理
curl -i 'http://127.0.0.1:8080/api/shop-type/list'
```

| 直接 Java | 代理入口 | 下一步 |
| --- | --- | --- |
| 连接不上 | 同样失败 | 看 Java 启动、端口、依赖 |
| 正常 JSON | 失败或返回 HTML | 看 Nginx /api 转发与地址是否正确 |
| success=false | 同样失败 | 看业务错误与 Java 日志 |
| 正常 JSON | 正常 JSON | 看浏览器实际请求 URL、HTTP 状态和前端解析 |

第三步查看有限条日志，而不反复重建整个数据环境：

```bash
docker compose -p hm-dianping -f dev/docker-compose.yml logs --tail=150 java
docker compose -p hm-dianping -f dev/docker-compose.yml logs --tail=100 web
```

Java 异常处理可能返回 HTTP 200 的 `success=false`，因此状态码只是第一层判断。排障记录要包含 HTTP 状态和业务 success，不能说“200 所以没问题”。日志可能包含本地演示验证码，保存截图时不要把自己的验证码与 token 一起公开。

## 15. 秒杀排障练习：把一次 PROCESSING 拆成三段

先拿本人接口返回的 orderId，后面所有查询都围绕这个 ID，不在不同请求之间随意切换。分段如下：

```text
尚未完成持久交接？   Stream pending / lag → 预约登记 → Outbox 是否存在
交接后尚未发送？     Outbox state / due / attempts / last_error
已发送尚未履约？     业务消费失败 / Inbox / 预约状态 / 正式订单
```

有 Outbox 且 Stream 已 ACK，不表示请求丢了；恢复责任可能已经交给数据库任务。pending 很多也不必然表示永久失败，可能是处理时间尚未达到接管条件。必须把等待时间、尝试原因和持久事实放在一起看。

管理员只读入口和字段查询示例在 [附录](附录-接口配置与数据字典.md)。确认根因前不要手动 XACK、覆盖库存或直接 UPDATE 预约成功，这些动作会改变恢复证据。需要恢复时，使用现有的按指定对象操作的接口，并复查结果。

<a id="section-15-01"></a>

### 一份故障记录应该保存哪些字段

```text
发生时间与服务版本：
用户看到的现象：
对象 ID（orderId / eventId / voucherId）：
接口的 HTTP 状态和 success：
相关持久状态与 attempts：
组件指标和关键错误：
定位到的窗口：
采取的指定操作：
恢复完成的业务证据：
没有覆盖的剩余风险：
```

这份记录也是面试资料。它能说明你不是随机重启碰巧恢复，而是沿明确的责任交接找到阻塞位置。

## 16. 常见问题速查

| 现象 | 优先检查 | 怎样判断 |
| --- | --- | --- |
| 8080 打不开 | Docker、web 状态、端口占用 | 先 `ps -a`，再 web 日志 |
| 页面在但数据不加载 | Java 是否启动、`/api` 代理 | 直接请求 8081 的公开读接口 |
| Java 启动很慢 | Maven 下载、MySQL 健康、Flyway | 读完整启动日志，不反复删卷 |
| 登录没有短信 | 本地未接短信服务 | 看 Java 这次验证码日志 |
| token 存在仍 401 | 请求头、过期、标签页 sessionStorage | 业务头不要加 Bearer |
| 登录了却 403/管理失败 | 管理员 ID 与服务环境 | `user/me` 对照 HMDP_ADMIN_IDS |
| 429 | 入口窗口、代理 IP 共享 | 等窗口恢复，不循环猛点 |
| 缓存一直无 MySQL 路径 | 已被预热 | 这是命中，不能要求首次必冷读 |
| 体验页提示未启用 | experience flag | 重新创建 Java 才刷新 env |
| 浏览回执不齐 | 有界丢弃、Kafka/消费、数据库 | 按 eventId 刷新，不盲目重发 POST |
| 匿名 UV=0 | 当前 UV 只统计登录用户 | 不等于 PV 也为 0 |
| 秒杀无可领取活动 | 当前时间、状态、库存、发布任务 | 不用过期日期或伪造活动 |
| 订单长期 PROCESSING | Stream/预约/Outbox/MQ | 沿同一个订单 ID 查持久事实 |
| SUCCESS 但未付款 | 预约与订单状态不同 | 看订单 status 与金额快照 |
| 数据库直改页面还是旧值 | CDC、检查点、版本、TTL | 应用更新与直改分别判断 |
| 上传或图片 404 | 上传目录权限、Nginx imgs 挂载 | 文件存在与归属登记分别检查 |
| Flyway 报校验错误 | 修改了已执行迁移 | 核对版本，不盲目清历史表 |

## 17. 秒杀卡住的完整排查顺序

1. 用本人请求状态接口确认 PROCESSING/REVIEW/SUCCESS/FAILED，不先重复创建动作。
2. 管理员查询预约任务、死信，确认 orderId、userId、voucherId 是否一致。
3. 查 Stream pending，判断消息是否尚未交接，是否在等待接管。
4. 查对应 SECKILL_FULFILL Outbox，判断发送失败还是已发送未消费。
5. 检查 MQ 组件与错误原因，修复依赖。
6. 对需复核记录执行受控重试；只有明确业务失败才走指定失败与补偿。
7. 重新查订单与对账，不用仅“HTTP 返回成功”判定恢复完成。

`retry` 和 `fail` 都是有业务后果的管理员动作。共享环境先明确影响对象，不批量覆盖未知任务；自己的隔离演示环境可以按测试设计复现。

<a id="section-18"></a>

## 18. 数据恢复的现实边界

MySQL 需要持久卷与备份，Redis 预占依赖 AOF 与存储，Canal 依赖 binlog 与订阅元数据，Broker 日志有保留期。Docker named volume 保存不等于具备备份和容灾。

数据库可重建很多投影，但验证码、登录和签到不是都可重建；Redis 尚未交接的秒杀请求也可能没有数据库事实。不要用全量 `FLUSHALL` 或 `down -v` 当通用排障手段。

告警没有配置外部通知时，只能在本地 UI 观察。准备分享部署时，应补充备份、真实告警通道和维护说明；当前 Wiki 已说明这些边界，不替代实际生产运维建设。

<a id="section-19"></a>

## 19. 可照做的排障方法：建立假设、找证据、验证恢复

<a id="section-19-01"></a>

### 第一步把“不能用”改成一个可观察问题

“项目坏了”无法决定该看哪个组件；“普通用户请求本人订单返回 401”“秒杀预约 30 秒保持 PROCESSING”“浏览 eventId 一直没有事实记录”才是具体问题。记录发生时间、URL、HTTP 状态、业务 success、用户身份范围和对象 ID，先把现象说清。

不要把登录 token、完整个人信息和数据库密码粘贴到故障报告。需要的是对象关联与状态证据，而不是复制所有请求内容。当前日志只有分秒毫秒，查跨天问题时结合 Docker 日志时间、数据库时间和 sampledAt，避免错对两个不同时间段。

<a id="section-19-02"></a>

### 第二步先读状态，再决定是否重试

| 当前证据 | 可以形成的假设 | 下一步只读核对 |
| --- | --- | --- |
| 直连成功，代理失败 | Nginx 或服务发现异常 | 同一路径两次响应、web 日志、代理配置 |
| 本人接口 401 | 身份未恢复 | 请求头格式、Redis token Hash、是否同一会话 |
| 管理入口 403 | 身份存在但管理配置不匹配 | `/user/me` 的 ID、容器实际管理员配置 |
| Outbox 长期 PENDING | Relay 未领取或未到尝试时刻 | next_attempt_at、调度与开关 |
| Outbox 长期 SENDING | worker 没续租或处理慢 | lease_owner、lease_until、发送错误 |
| 普通事件长期 SENT | 发送成功但消费未持久完成 | 对应消费组、Inbox、消费失败记录 |
| 未来到期任务 SENT | 可能仍在正常等待 | deliver_at 与数据库当前时间 |
| 浏览回执 PENDING | 未落地或尽力采集丢失 | Kafka 运行、失败记录、事实表 |

每个假设都只是下一步调查方向，不是已经确认的根因。例如 SENT 没有统一含义：普通创建事件等待很久与未来关单等待很久，判断依据不同。

<a id="section-19-03"></a>

### 第三步保持同一身份追踪，不靠新增请求冲掉证据

普通订单用 orderId 关联业务 Outbox 与事件历史；Kafka 用原 eventId 查询事实；秒杀用原预约订单号关联准入、预约、履约任务和订单。一个链路里出现多个 ID 时，把映射写进记录，不要随便拿当前最新的一条代替出问题的那条。

频繁刷新店铺可能产生新的浏览事件；重复点击体验采集会生成新 UUID；重新发布活动可能改变原有运行状态。新增成功请求不能证明旧任务已经恢复。排障时先保存原证据，再用只读查询定位责任人。

<a id="section-19-04"></a>

### 四个案例的判断过程

**案例一：首页样式正常，店铺列表为空。**

先看 Network 的分类和 catalog 请求：若根本没发请求，查页面脚本；若返回 HTML，查路径和代理；若 HTTP 200 但 success=false，按 errorMsg 找参数或业务拒绝；若成功且数组为空，再看筛选条件与实际库。静态文件成功不排除后端断开，数组为空也不等于网络坏了。

**案例二：创建订单后页面显示成功，创建事件没完成。**

先看订单是否已存在、Outbox 是否同事务留下。不存在时回到订单事务；存在且 PENDING 时看 Relay；SENT 时看消费；DONE 时看对应事件历史与观察接口是否查错 ID。不要因为后台事件没推进就让用户无依据地取消一个已成功创建的订单。

**案例三：三条浏览事件只有两条 PERSISTED。**

保留三个原 UUID，查询是否同一店铺、同一时间范围。浏览是尽力发送，第三条暂时未落地不自动触发可靠 Outbox 补发。继续看 Kafka 消费、失败记录和采集异常；不能用“提交数 3”作“成功落库数 3”的断言。

**案例四：数据库直改店铺后页面仍旧。**

确认 UPDATE 提交到当前 hmdp 库，检查 Canal 过滤和 Java CDC 状态，再核对检查点、缓存失效与短副本时间。若应用写接口正常而直改不传播，优先看 CDC 路径；若两者都不传播，再看共同缓存与查询对象。恢复原店铺名称也应有一轮传播证据。

<a id="section-19-05"></a>

### 第四步做恢复前，先写预期结果

处理前写下“不应该发生的副作用”：重驱动消息不能生成第二份订单，补偿旧预约不能释放新预约，关闭扫描不能覆盖已支付，缓存失效不能清掉签到或 Stream。恢复步骤必须围绕这些规则，并使用已有业务恢复入口。

先确认根因已经去除，再按原身份重试；观察最终事实、任务状态和错误计数是否收敛。只看到接口返回成功不够，例如重试接口可能只重新排队，后续消费仍需要继续检查。

故障注入使用第 3 节的独立测试 Compose 项目，组件停启和临时数据由该项目隔离。日常共享演示不需要为了展示亮点暂停 Broker、删除卷或手动改预约状态；已有隔离测试可以提供相应证据。

<a id="section-19-06"></a>

### 第五步把修复变成一个可重复断言

出现旧回填问题，应把旧加载暂停在明确位置，完成更新失效后再放行，而不是增加随机 sleep 期待撞上。出现重复消息问题，应投递同一身份、比较业务记录与汇总值，而不是仅断言没有抛异常。

异步测试应等待有意义的条件并设置超时，例如原 eventId 事实存在、指定订单状态完成。超时时输出对象状态和任务错误；过短固定等待会让正常慢机器随机失败，过长无界等待会掩盖真正卡住。
