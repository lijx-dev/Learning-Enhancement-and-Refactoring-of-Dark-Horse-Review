## 1. 发布笔记是一条完整业务链

发布时不能只相信前端的 authorId 和图片路径。当前服务从 `UserHolder` 设置作者，清除客户端传来的 ID、点赞数和时间等字段，校验店铺存在、标题/正文长度与图片数量；图片必须属于当前账号且处于可用状态。

笔记、图片引用与 FEED Outbox 在同一数据库事务保存。发布成功说明笔记已持久化，粉丝收到 Feed 可能还需要等待异步投影。

源码：[BlogServiceImpl](../src/main/java/com/hmdp/service/impl/BlogServiceImpl.java)、[MediaServiceImpl](../src/main/java/com/hmdp/service/impl/MediaServiceImpl.java)。正文最多 10000 字符，图片最多 9 张且路径长度受限。列表批量读取作者与当前用户的点赞状态，减少每条笔记额外查询产生的 N+1 问题。

<a id="section-02"></a>

## 2. 点赞为什么建议使用明确状态接口

课程的 `PUT /blog/like/{id}` 是切换：已点赞就取消，未点赞就点赞。请求超时后重复发送，第二次可能把第一次成功的点赞又取消。它不是天然幂等。

扩展的 `PUT /blog/like/{id}/state?liked=true` 表示“设为已点赞”，重复发送结果仍是已点赞。`liked=false` 表示明确取消。Service 通过笔记行锁、持久点赞唯一键和事务更新计数，同时登记 LIKE 投影任务。

当前查询点赞状态和前几个点赞用户主要读数据库事实；Redis ZSet 是异步投影。课程中点赞用户只存 Redis 的方案不能直接套用来解释当前持久化能力。历史演示点赞数没有完整用户归属，新增持久点赞不会凭空还原所有历史点赞用户。

<a id="section-03"></a>

## 3. 关注与共同关注

`PUT /follow/{id}/true` 表示关注，false 表示取消。不能关注不存在的人，也不能关注自己。持久事实在 `tb_follow_edge`，唯一键防止重复边；FOLLOW 事件把当前关系投影到 Redis `follows:{userId}`。

课程用 Redis Set 交集讲共同关注；当前 `followCommons` 通过 Mapper 查询持久关系交集，Redis 投影不是这个查询的唯一事实来源。知道数据结构思想后，还要确认实际方法调用。

源码：[FollowServiceImpl](../src/main/java/com/hmdp/service/impl/FollowServiceImpl.java)、[FollowMapper.xml](../src/main/resources/mapper/FollowMapper.xml)。

<a id="section-04"></a>

## 4. Feed 推送与可续传

作者发布时，FEED 后台任务每次查询一批约 200 个粉丝，向粉丝 `feed:{userId}` 的 ZSet 写入笔记 ID，score 使用任务最初创建时间，并保存粉丝游标。一批处理完会完成这条事件；若还有粉丝，则在同一事务新增带续传游标的后续事件，保留最初时间，不在一个 HTTP 请求里循环所有粉丝。

ZSet 相同 member 重复写入不会生成两个成员，固定原始时间避免重试把旧笔记置顶。每个收件箱还限制保留约 1000 条。当前是推送模型，没有实现对大 V 的推拉混合和完整历史 Feed 重建入口。

普通页码不适合持续插入的新动态：第一页后面来了新笔记，第二页 offset 会移位。课程用 score 游标解决这个问题；当前 `GET /blog/of/follow?lastId=...&offset=...` 返回 `list`、`minTime`、`offset`。下一页传回 `minTime` 作为 lastId，传回 offset；遇到多条同时间戳要累计同分数偏移，不能每次从 0 开始。

数据库里有笔记和关注事实，不等于 Redis Feed 丢失后会自动完整重建。既有任务已完成的历史范围，需要额外恢复设计或重新生成投影。

<a id="section-05"></a>

## 5. 图片生命周期与并发删除

上传接受 jpg/jpeg/png/webp，限制体积并检查部分文件签名，不只是相信扩展名。随机文件名分散到目录，保存文件后登记 `tb_media_owner`。

删除时校验 owner、加行锁并检查 `tb_blog_media` 引用。正在被笔记使用的图片拒绝直接删除；可删除图片先标记 DELETING 并写媒体删除 Outbox，后台幂等删除文件，再标记 DELETED。

发布与删除都按同一资源行协调。多图片锁按稳定排序获取，降低互相交叉加锁的风险。否则会出现“发布校验刚通过，图片却被另一个请求删掉”的并发问题。

文件系统不参加数据库事务。当前上传仍存在“文件已写入但归属登记失败”导致孤儿文件的窗口；签名校验也不等于完整图片解码或恶意内容检测。对象存储、孤儿清理与更严格图片验证属于后续方向。

## 6. 商家搜索与 GEO

`/shop/search` 组合筛选要求 typeId，可传名称、商圈、均价、评分、可用券、经纬度、页码与排序。score/price/distance 是白名单排序，不让前端随意传 SQL 排序片段。列表展示入口 `/shop/catalog` 支持跨分类和关键词，参数范围以代码与附录为准。

课程附近查询使用 `shop:geo:{typeId}`：GEO 返回按距离排序的店铺 ID 与距离，Java 再批量读取数据库详情，并保留原 ID 顺序。不能让 SQL 的 IN 自行决定排序。

当前 `/shop/of/type` 有坐标且 GEO Key 存在时使用 GEOSEARCH，约 5 公里范围；新 Redis 没有课程 GEO 索引时，回退到组合查询。组合查询使用数据库坐标筛选与距离计算。没有 GEO 数据仍有结果，不表示 Redis GEO 已实际命中。

x 是经度，y 是纬度；评分 4.5 传 45；均价筛选单位是元。按距离排序必须同时提供合法 x/y，不能在新环境直接照搬一个城市坐标，然后误以为附近店铺为空是故障。

## 7. 从课程点赞计数推导持久点赞关系

<a id="section-07-01"></a>

### 为什么只给 liked 加一不够

如果用户重复点“赞”，每次都 `liked=liked+1`，同一人就能贡献很多票。计数只说明总量，不说明“谁已经点过”，因此要同时保存用户关系。

课程用 Redis ZSet 保存用户 ID 与点赞时间；当前新增 MySQL `tb_blog_like` 作为可恢复的关系事实，再异步投影到 ZSet。查询个人状态不应只依赖一个可能被清空的缓存。

<a id="section-07-02"></a>

### 切换与设定状态的不同

| 请求语义 | 第一次 | 第二次相同请求 | 是否适合自动重试 |
| --- | --- | --- | --- |
| toggle | 从未赞变已赞 | 从已赞变未赞 | 不能盲目重试 |
| liked=true | 设为已赞 | 仍为已赞 | 更适合 |
| liked=false | 设为未赞 | 仍未赞 | 更适合 |

当前两个 Controller 入口最终进入 updateLike。requested 为 null 表示切换，明确 boolean 表示目标状态。

以下为 [BlogServiceImpl.java](../src/main/java/com/hmdp/service/impl/BlogServiceImpl.java) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```java
private Result updateLike(Long id, Boolean requested) {
  long user = UserHolder.getUser().getId();
  return transactions.execute(
      tx -> {
        if (baseMapper.selectIdForUpdate(id).isEmpty()) {
          return Result.fail("笔记不存在");
        }
        boolean current = baseMapper.countLike(id, user) > 0;
        boolean desired = requested == null ? !current : requested;
        if (current == desired) {
          return Result.ok();
        }
        if (desired) {
          baseMapper.insertLike(id, user);
          baseMapper.incrementLikes(id);
        } else {
          baseMapper.deleteLike(id, user);
          baseMapper.decrementLikes(id);
        }
        outbox.appendBusinessEvent("LIKE", id, user);
        return Result.ok();
      });
}
```


先锁笔记行，确认存在；查当前用户关系；目标和当前相同时直接返回；否则修改关系与计数，再登记 LIKE 事件。关系、计数和待投影任务在同一事务，不把“计数改了但关系没了”当正常结果。

<a id="section-07-03"></a>

### ZSet 的 score 为什么放时间

member=userId 保证用户不重复，score=点赞时间可以按时间选用户。它不是评分大小，也不是点赞总数。课程前几位点赞用户与热门笔记按总点赞量是两种排行榜，不能混为一个 Key。

当前前几个用户查询读持久事实；异步 ZSet 能用于投影与学习，但不代表所有列表都从 ZSet 取数。

<a id="section-07-04"></a>

### 列表为什么批量补作者和个人状态

以下为 [BlogServiceImpl.java](../src/main/java/com/hmdp/service/impl/BlogServiceImpl.java) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```java
private void enrich(List<Blog> blogs) {
  if (blogs.isEmpty()) {
    return;
  }
  List<Long> authorIds =
      blogs.stream().map(Blog::getUserId).distinct().collect(Collectors.toList());
  Map<Long, User> authors =
      userService.listByIds(authorIds).stream().collect(Collectors.toMap(User::getId, u -> u));
  Set<Long> likedIds = new HashSet<>();
  if (UserHolder.getUser() != null) {
    likedIds.addAll(
        baseMapper.selectLikedBlogIds(
            UserHolder.getUser().getId(),
            blogs.stream().map(Blog::getId).collect(Collectors.toList())));
  }
  for (Blog blog : blogs) {
    User author = authors.get(blog.getUserId());
    if (author != null) {
      blog.setName(author.getNickName());
      blog.setIcon(author.getIcon());
    }
    blog.setIsLike(likedIds.contains(blog.getId()));
  }
}
```


先从一页笔记提取去重作者 ID，一次 listByIds；当前用户的点赞状态也按整页笔记 ID 批量读，随后在内存组装。假设一页有 10 条，逐条查作者和点赞会多出约 20 次附加查询；批量查询将这类 N+1 扩大效应压缩。

批量优化不等于所有接口都零附加查询。例如单笔记详情仍可按对象查询；应结合请求规模选择，不把通用口号当全站已优化证明。

## 8. 从 Set 共同关注推导当前关系查询

教学 Set 示例：A 关注 {1,2,3}，B 关注 {2,3,4}，交集为 {2,3}。Redis 可以用 SINTER 演算；集合 member 表示用户 ID，不要把用户名当唯一身份。

```text
SADD tutorial:follow:a 1 2 3
SADD tutorial:follow:b 2 3 4
SINTER tutorial:follow:a tutorial:follow:b
DEL tutorial:follow:a tutorial:follow:b
```

以上仅在自己的练习环境使用 tutorial Key。实际共同关注查询使用数据库持久边：

以下为 [FollowMapper.xml](../src/main/resources/mapper/FollowMapper.xml) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```sql
SELECT a.follow_user_id
FROM tb_follow_edge a
JOIN tb_follow_edge b ON a.follow_user_id=b.follow_user_id
WHERE a.user_id=#{userId} AND b.user_id=#{otherUserId} LIMIT 100
```

以下为 [FollowServiceImpl.java](../src/main/java/com/hmdp/service/impl/FollowServiceImpl.java) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```java
public Result follow(Long target, Boolean enabled) {
  long user = UserHolder.getUser().getId();
  if (target == null || target == user || userService.getById(target) == null) {
    return Result.fail("关注对象无效");
  }
  return transactions.execute(
      tx -> {
        int changed =
            Boolean.TRUE.equals(enabled)
                ? baseMapper.insertEdge(user, target)
                : baseMapper.deleteEdge(user, target);
        if (changed > 0) {
          outbox.appendBusinessEvent("FOLLOW", target, user);
        }
        return Result.ok();
      });
}
```


两个别名 a/b 找同一个 follow_user_id，再限定各自 user_id。这表达集合交集，而不要求当前 Redis Set 已投影完成。查询最多取一批，不能称为无限规模完整分页接口。

关注指定 true/false 可重复，只有真实关系变化才写后续任务。取消关系后迟到的旧 FOLLOW 消息读取的是当前关系，不应重新把已取消的人塞回 Set。

## 9. 从普通分页推导 Feed 游标

<a id="section-09-01"></a>

### 为什么 page=2 会重复

原来按时间倒序有 [A,B,C,D]，第一页取 [A,B]。随后更晚 X 插入，列表变成 [X,A,B,C,D]。第二页按 offset=2 取 [B,C]，B 重复。游标让下一页从上次边界继续，而不是依赖不断变动的位置。

<a id="section-09-02"></a>

### 时间相同为什么还要 offset

假设 score 序列为 [100,90,90,90,80]，每页 2 条：

| 页 | max/offset 输入 | 返回 score | 下一页参数 |
| --- | --- | --- | --- |
| 1 | 足够大的 max、0 | 100,90 | max=90, offset=1 |
| 2 | 90、1 | 90,90 | max=90, offset=3 |
| 3 | 90、3 | 80 | max=80, offset=1 |

当 minTime 仍等于输入 max，新偏移累加旧 offset；跨到更小时间时重新计数。仅传时间会重复同分记录，简单 `score<max` 又会漏掉尚未返回的同分记录。

以下为 [BlogServiceImpl.java](../src/main/java/com/hmdp/service/impl/BlogServiceImpl.java) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```java
public Result queryBlogOfFollow(Long max, Integer offset) {
  // 1.获取当前用户
  Long userId = UserHolder.getUser().getId();
  // 2.查询收件箱 ZREVRANGEBYSCORE key Max Min LIMIT offset count
  String key = RedisConstants.FEED_KEY + userId;
  Set<ZSetOperations.TypedTuple<String>> typedTuples =
      stringRedisTemplate.opsForZSet().reverseRangeByScoreWithScores(key, 0, max, offset, 2);
  // 3.非空判断
  if (typedTuples == null || typedTuples.isEmpty()) {
    return Result.ok();
  }
  // 4.解析数据：blogId、minTime（时间戳）、offset
  List<Long> ids = new ArrayList<>(typedTuples.size());
  long minTime = 0; // 2
  int os = 1; // 2
  for (ZSetOperations.TypedTuple<String> tuple : typedTuples) { // 5 4 4 2 2
    // 4.1.获取id
    ids.add(Long.valueOf(tuple.getValue()));
    // 4.2.获取分数(时间戳）
    long time = tuple.getScore().longValue();
    if (time == minTime) {
      os++;
    } else {
      minTime = time;
      os = 1;
    }
  }

  // 5.根据id查询blog
  String idStr = StrUtil.join(",", ids);
  List<Blog> blogs = query().in("id", ids).last("ORDER BY FIELD(id," + idStr + ")").list();

  enrich(blogs);
  // 6.封装并返回
  ScrollResult r = new ScrollResult();
  r.setList(blogs);
  r.setOffset(minTime == max ? offset + os : os);
  r.setMinTime(minTime);

  return Result.ok(r);
}
```


取 ZSet 记录后，用 ID 查 MySQL 并保持原顺序，再补作者与点赞。max 是时间边界，不是笔记 ID；URL 参数叫 lastId 是历史命名，不应因此传一个订单号。

<a id="section-09-03"></a>

### 粉丝推送为什么分批

假设粉丝 450 人，每批 200，需要 200+200+50 三次。当前任务保存 cursor_id，并创建续传事件，而不是在 Web 请求里把三批全循环完。created_at 沿用原发布任务，Feed score 不因重试改变。

以下为 [FollowMapper.xml](../src/main/resources/mapper/FollowMapper.xml) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```sql
SELECT id,user_id
FROM tb_follow_edge
WHERE follow_user_id=#{authorId} AND id>#{cursorId} AND created_at<=#{publishedAt}
ORDER BY id LIMIT 200
```


id>cursor 支持按稳定关注边 ID 继续，created_at<=publishedAt 限定发布时已存在的关注边。后来关注者不一定自动收到发布前历史，这是当前语义。取消后的在途推送、长期历史重建与大 V 写放大仍是后续产品/架构需要明确的边界。

## 10. 图片从上传到引用再到删除的状态推导

用户上传成功后，图片是他可使用的资源；发布笔记把它变成被引用的资源。要同时防止他盗用别人的路径，以及删掉已被内容引用的图片。

| 动作 | 需要的事实 | 竞争对象 |
| --- | --- | --- |
| 上传 | 文件写成功、归属登记 | 路径与当前用户 |
| 发布引用 | 本人 ACTIVE 图片 | 图片 owner 行 |
| 请求删除 | 本人、无引用、状态可删 | 同一 owner 行及引用 |
| 后台删除 | DELETING 对应任务 | 幂等外部文件操作 |

```java
public boolean lockOwnedImages(String images, long user) {
  if (!TransactionSynchronizationManager.isActualTransactionActive()) {
    throw new IllegalStateException("图片引用需要业务事务");
  }
  try {
    // All publishers lock paths in the same order; deletion locks the same owner row.
    for (String path : paths(images)) {
      List<Map<String, Object>> rows = mediaMapper.selectOwnerForUpdate(path);
      if (rows.isEmpty()
          || ((Number) rows.get(0).get("user_id")).longValue() != user
          || !"ACTIVE".equals(rows.get(0).get("state"))) {
        return false;
      }
    }
    return true;
  } catch (IllegalArgumentException invalid) {
    return false;
  }
}
```

```java
public Result delete(String input, long user) {
  final String path;
  try {
    path = MediaStorage.normalize(input);
  } catch (IllegalArgumentException invalid) {
    return Result.fail(invalid.getMessage());
  }
  return transactions.execute(
      tx -> {
        List<Map<String, Object>> rows = mediaMapper.selectOwnerForUpdate(path);
        if (rows.isEmpty() || ((Number) rows.get(0).get("user_id")).longValue() != user) {
          return Result.fail("图片不存在或无权删除");
        }
        if (!"ACTIVE".equals(rows.get(0).get("state"))) {
          return Result.ok();
        }
        if (!mediaMapper.selectReferencesForUpdate(path).isEmpty()) {
          return Result.fail("图片已用于笔记，不能直接删除");
        }
        mediaMapper.markDeleting(path);
        outbox.appendMediaDeletionEvent(path, user);
        return Result.ok();
      });
}
```


发布和删除对同一 owner 行加锁。假设发布先拿到锁并插入引用，删除随后看到引用就拒绝；若删除先标 DELETING，发布随后发现不 ACTIVE 就不能引用。这个规则要靠后端事务，不能只在 UI 隐藏删按钮。

图片路径先 normalize，不能接受任意文件系统路径。所有图片按稳定顺序锁定，减少“请求 A 先锁图1再图2，B 先锁图2再图1”的交叉死锁风险。

文件删除在数据库外发生，重复删除应安全。上传“先写文件再登记 owner”仍可能留下孤儿文件；文档明确这个窗口，不能把资源状态设计宣传为已解决所有存储问题。

### GEO 存什么，数据库仍存什么

GEO 索引保存 shopId 与坐标，查到位置后还需要 MySQL 的名称、价格、评分和营业信息。索引位置不是完整店铺对象，也不是交易权限。

```text
GEOADD tutorial:geo 121.50 31.20 shop-a 121.51 31.20 shop-b
GEOSEARCH tutorial:geo FROMLONLAT 121.50 31.20 BYRADIUS 2 km WITHDIST ASC
DEL tutorial:geo
```

这是独立练习坐标。真实演示数据可能在另一城市，不应拿练习坐标解释店铺为空。

<a id="section-11-02"></a>

### 课程查询的两段流程

先按类别 Key 查询附近且距离升序的前 end 条，再跳过前 from 条；拿结果 ID 按原顺序查询数据库并设置 distance。Redis 返回 5,1,3，SQL IN 不保证也返回 5,1,3，所以需要保序。

以下为 [ShopServiceImpl.java](../src/main/java/com/hmdp/service/impl/ShopServiceImpl.java) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```java
public Result queryShopByType(Integer typeId, Integer current, Double x, Double y) {
  // 1.判断是否需要根据坐标查询
  if (x == null || y == null) {
    // 不需要坐标查询，按数据库查询
    Page<Shop> page =
        query()
            .eq("type_id", typeId)
            .page(new Page<>(current, SystemConstants.DEFAULT_PAGE_SIZE));
    // 返回数据
    return Result.ok(page.getRecords());
  }

  // 2.计算分页参数
  int from = (current - 1) * SystemConstants.DEFAULT_PAGE_SIZE;
  int end = current * SystemConstants.DEFAULT_PAGE_SIZE;

  // 3.查询redis、按照距离排序、分页。结果：shopId、distance
  String key = SHOP_GEO_KEY + typeId;
  // A fresh Redis has no course GEO fixtures; the default page must still show nearby shops.
  if (!Boolean.TRUE.equals(stringRedisTemplate.hasKey(key))) {
    ShopSearchDTO criteria = new ShopSearchDTO();
    criteria.setTypeId(typeId.longValue());
    criteria.setX(x);
    criteria.setY(y);
    criteria.setPage(current);
    criteria.setSize(SystemConstants.DEFAULT_PAGE_SIZE);
    criteria.setSort("distance");
    return searchShops(criteria);
  }
  GeoResults<RedisGeoCommands.GeoLocation<String>> results =
      stringRedisTemplate
          .opsForGeo() // GEOSEARCH key BYLONLAT x y BYRADIUS 10 WITHDISTANCE
          .search(
              key,
              GeoReference.fromCoordinate(x, y),
              new Distance(5000),
              RedisGeoCommands.GeoSearchCommandArgs.newGeoSearchArgs()
                  .includeDistance()
                  .sortAscending()
                  .limit(end));
  // 4.解析出id
  if (results == null) {
    return Result.ok(Collections.emptyList());
  }
  List<GeoResult<RedisGeoCommands.GeoLocation<String>>> list = results.getContent();
  if (list.size() <= from) {
    // 没有下一页了，结束
    return Result.ok(Collections.emptyList());
  }
  // 4.1.截取 from ~ end的部分
  List<Long> ids = new ArrayList<>(list.size());
  Map<String, Distance> distanceMap = new HashMap<>(list.size());
  list.stream()
      .skip(from)
      .forEach(
          result -> {
            // 4.2.获取店铺id
            String shopIdStr = result.getContent().getName();
            ids.add(Long.valueOf(shopIdStr));
            // 4.3.获取距离
            Distance distance = result.getDistance();
            distanceMap.put(shopIdStr, distance);
          });
  // 5.根据id查询Shop
  String idStr = StrUtil.join(",", ids);
  List<Shop> shops = query().in("id", ids).last("ORDER BY FIELD(id," + idStr + ")").list();
  for (Shop shop : shops) {
    shop.setDistance(distanceMap.get(shop.getId().toString()).getValue());
  }
  // 6.返回
  return Result.ok(shops);
}
```


无坐标走普通数据库分类分页。有坐标但 GEO Key 不存在时，回退组合搜索；Key 存在却当前位置附近没有结果，不应又偷偷返回所有远处店铺来伪装“有数据”。

### 组合附近查询的候选框与精确距离

数据库路径先用经纬度范围缩小候选，再用球面距离公式筛 5km，排序与分页在数据库完成，避免把全部店铺加载进 Java 堆。经度跨度与纬度相关，靠近极区等特殊坐标边界仍需要正式规模的空间查询评估。

```java
/**
 * 在同一个请求缓存作用域中读取同一店铺两次，记录每次经过的缓存层与耗时。
 *
 * <p>用于观察请求级复用；不会主动清空缓存制造命中结果。
 */
@Override
public Result traceShopCacheReads(Long shopId) {
  if (!enabled) {
    return Result.fail("体验观察接口未启用");
  }
  if (shopId == null || shopId <= 0) {
    return Result.fail("请选择有效店铺");
  }
  List<Map<String, Object>> reads = new ArrayList<>();
  String shopName = null;
  try (RequestCacheScope scope = RequestCacheScope.open()) {
    for (int index = 0; index < 2; index++) {
      try (CacheReadTrace trace = CacheReadTrace.open()) {
        long started = System.nanoTime();
        Result loaded = shopService.queryById(shopId);
        if (!Boolean.TRUE.equals(loaded.getSuccess()) || loaded.getData() == null) {
          return loaded;
        }
        shopName = ((Shop) loaded.getData()).getName();
        Map<String, Object> read = new LinkedHashMap<>();
        read.put("sequence", index + 1);
        read.put("durationMicros", TimeUnit.NANOSECONDS.toMicros(System.nanoTime() - started));
        read.put("events", trace.snapshot());
        reads.add(read);
      }
    }
  }
  Map<String, Object> result = new LinkedHashMap<>();
  result.put("requestId", UUID.randomUUID().toString());
  result.put("shopId", shopId);
  result.put("shopName", shopName);
  result.put("reads", reads);
  return Result.ok(result);
}
```


同请求开 scope 后循环读两次；每次开 trace 并记录耗时，正常调用 shopService.queryById。CacheClient 真正经过哪一层才记录该层事件。返回带 requestId 与 sequence，让前端能把三次 HTTP 与每次两读区分开。

采样 scope/trace 用 try-with-resources 关闭，确保异常也能恢复上下文；记录最多有限条，不持久保存真实实体内容。这个观察器不是一套自动采集全站所有请求的 APM。

提交返回这次三条 UUID；查询逐个去行为事实表找。PERSISTED 表示消费已登记，PENDING 表示暂时未查到，可能还在路上或已丢失，不能立即当作错误原因已确定。

## 17. 社区与搜索的用户操作、并发边界和验收

<a id="section-17-01"></a>

### 点赞先区分“切换”和“设为已点赞”

切换接口表达“把当前状态反过来”：连续两个请求可能从未点赞变为点赞再变回未点赞。明确状态接口表达“我要处于点赞状态”：相同请求重试仍应保持点赞。用户双击、网络超时重试时，后者更容易保持意图。

数据库点赞关系回答“谁点过哪篇”，笔记 liked 回答汇总数量；这两个变化需要协调，不能只更新数量。Redis ZSet 提供时间排序副本，失败后通过任务读取当前关系补投影，而不是相信迟到事件一定仍代表当前意图。

设先点赞、后取消，取消事件先消费，旧点赞事件后到。若旧事件机械 ZADD 就会把取消撤销。当前投影读取持久关系的现状，当前不存在就 ZREM；配合同一关系投影的串行控制，迟到旧任务不会仅因名称叫 LIKE 就强制恢复旧态。

<a id="section-17-02"></a>

### 关注是一条有方向的边

用户甲关注乙，表示甲的“关注的人”包含乙，乙的“粉丝”包含甲，反过来并不自动成立。共同关注比较甲和丙都关注了谁，不是比较他们共同有哪些粉丝。

Set 交集是课程中理解共同关注的直观方式，当前持久关系查询与投影保证服务重启后还能恢复事实。阅读 DAO 时先看 `user_id` 与 `follow_user_id` 的方向，否则很容易把粉丝查询写成关注列表。

异步关系副本可能稍后变化。验收先确认持久接口的当前状态，再观察 Redis 投影，不要求两者在消息尚未消费时同时变化。取消后旧任务到达也应该保持取消结果。

<a id="section-17-03"></a>

### Feed 有两套游标，不能混用

浏览者下拉 Feed 的游标用于读取 ZSet：按发布时间向前翻，时间相同时还需要 offset，避免边界重复或跳过。后台推送给粉丝的游标则是关注关系行 ID，用于继续扫描下一批粉丝。它们都叫“游标”，含义、保存位置和消费者完全不同。

设同一发布时间有三篇笔记，一页只能返回两篇。下一页只把 max 改成更早时间，会跳过第三篇；仍用原 max 但无 offset，会重复前两篇。这是读取侧游标保留“同一分数已读取数量”的原因。

<a id="section-17-04"></a>

### 201 位粉丝为什么值得专门做测试

当前后台每批 200 人，作者有 201 位满足条件的粉丝时，第一个任务处理前 200，推进关注关系 ID 游标，并持久登记下一批；下一批完成剩余 1 人。这个数字刚好跨边界，能验证续传是否真正生效。

首批满 200 时即使恰好只有 200 位，仍可能登记续传，下一批为空后结束，这是按批大小判断完成的正常现象。不能因产生了空尾批就断言推送错了。

续传沿用原 createdAt 作为发布时间，也用于过滤发布时间之后才建立的关注关系。若改成续传时刻，会改变排序和粉丝范围。当前查询检查关系 created_at，但没有完整历史关注版本，不能宣传成任意历史时点的粉丝快照查询。

单人的 Feed 最多保留 1000 条，是当前查询副本的容量边界，不是笔记业务总数最多 1000。测试需要同时看没有重复条目、剩余粉丝收到、时间不被续传刷新；消息任务 DONE 只代表当前一批完成，还应检查是否有后续批次。

<a id="section-17-05"></a>

### 图片为什么要先保存归属，再登记引用

上传成功产生图片资源，不代表任何用户都可以把路径填进笔记。发布时要校验当前用户拥有且资源 ACTIVE，然后登记笔记引用。删除时同样要检查归属与引用，避免删掉别人正在使用或已被笔记引用的文件。

资源进入 DELETING 后，新的引用不应再建立。文件删除由异步任务完成，之后持久状态改为 DELETED。如果文件已删但数据库完成登记前失败，重试删除同一文件需要安全；不能要求数据库回滚自动还原磁盘文件。

只看路径存在不能说明有权使用，只看数据库资源记录也不说明磁盘文件还在。排查图片故障时分开查看归属、资源状态、笔记引用和实际文件，再定位哪一环不一致。

<a id="section-17-06"></a>

### 附近搜索先弄清单位和两条实现路径

课程分类附近商户查询使用 Redis GEO 取得 ID 与距离，再回数据库补详情；组合筛选路径在 MySQL 中做候选范围、距离过滤、排序和分页。不能因为项目有 GEO 就说所有搜索都只查 Redis。

经度 x、纬度 y 不能反写。半径与最终距离按实际接口字段说明使用，金额筛选 maxPrice 用元，minScore=45 表示 4.5 分。把半径米数当公里，或把价格分数当元数，会得到看似“搜索没有数据”的错误输入。

GEO 候选顺序与数据库 IN 查询顺序也不同。拿到近到远 ID 后回库，需要保持原排序，否则展示的距离标签正确，列表先后却错误。组合筛选还要检查页码、尺寸和合法 sort，而不是从浏览器任意拼接排序 SQL。

<a id="section-17-07"></a>

### 用两位用户完成社区验收

甲发布一篇带自己图片的笔记；乙关注甲并点赞；甲再发布一篇，让乙观察关注 Feed。随后乙取消点赞和关注，确认持久状态与延迟投影最终收敛。使用独立浏览器会话保存两个用户身份，避免在同一会话中切账号后误以为是两个人。

普通页面可以验证功能闭环，200 人边界、删除与引用竞争、旧事件乱序需要隔离测试控制窗口。交付给别人时，将可自行操作的页面步骤与已有故障证据区分，让普通访客不必手改数据库也能理解亮点。
