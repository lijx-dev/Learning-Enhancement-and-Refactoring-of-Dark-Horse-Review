## 1. 用一个生活场景认识项目

小明想找附近一家评分高、价格合适的餐厅。他先在首页选分类，按名称或价格筛选，打开店铺查看地址和优惠券，然后看其他人的探店笔记。喜欢某个作者后，他可以关注作者，在关注动态中查看新笔记。小明登录后领取普通优惠券，遇到限时优惠时参加秒杀，在订单页查看结果。

这个过程中系统至少要回答这些问题：店铺数据从哪里来？每天反复访问热门店铺会不会压垮数据库？一百个人抢十张券会不会卖出十一张？领取按钮点两次会不会生成两个订单？服务突然退出后，已受理的请求还能不能继续处理？消息重复收到后，热榜会不会重复计数？

这些问题把看起来普通的点评网站，变成一个可以学习缓存、并发、数据库事务和消息可靠性的完整项目。

## 2. 从一个点击拆出整个项目

<a id="section-02-01"></a>

### 先明确用户在做什么

假设小明依次完成四件事：打开店铺、登录、领取普通券、参与秒杀。前端按钮很相似，但后端的完成标准完全不同。

| 用户动作 | 输入来自哪里 | 后端要保证什么 | 什么时候算完成 |
| --- | --- | --- | --- |
| 打开店铺 | URL 的 shopId | 返回可展示数据，允许短期副本 | 数据返回 |
| 登录 | 手机号与一次性验证码 | 证明身份，创建令牌 | token 保存成功并返回 |
| 领普通券 | 券 ID + 登录身份 | 不重复创建有效订单，固定价格 | MySQL 事务提交 |
| 抢秒杀券 | 活动券 ID + 登录身份 | 不超预占、不重复占资格、能追踪履约 | 入口先受理，最终查询落库状态 |

初学者最常见的误解是“返回 success=true 就已经完成所有事情”。店铺读取、普通建单和异步秒杀的 success 含义不同，必须由接口契约解释。

<a id="section-02-02"></a>

### 第一阶段：只有网页和数据库能不能做

可以。Java 收到请求后查询数据库并返回，普通规模下能完成查店、登录和建单。我们加 Redis、消息队列并不是为了让功能“从不能用变成能用”，而是解决规模扩大、重复操作和组件故障后的问题。

例如热门店铺每秒收到 1000 次相同查询，如果每次都查数据库，同一份记录被反复读取。缓存将重复结果放在更近的位置，让数据库处理其他工作。

再例如一个作者有很多粉丝，发布笔记时如果同步遍历所有粉丝，用户会一直等。后台任务能缩短发布请求，但这时必须补充进度、持久化和重试，不能只把循环丢进一个新线程。

<a id="section-02-03"></a>

### 第二阶段：哪些动作适合晚一点完成

把操作分成“用户必须立刻知道的”与“可以稍后完成的”。普通订单事实必须先保存，用户才能拿到可查订单；粉丝 Feed、缓存失效的后续补偿和分析热榜允许短暂滞后。秒杀入口必须立即决定能否预占，但订单履约可以后台完成，前提是保留查询状态。

异步增加的不是一条队列，而是一整套新问题：请求退出后任务保存在哪里？谁继续处理？完成前用户查什么？任务重复执行怎么办？处理失败谁知道？本项目的可靠性扩展围绕这些问题建立。

<a id="section-02-04"></a>

### 第三阶段：用“事实、副本、任务”认识数据

| 类别 | 示例 | 删除后有什么后果 |
| --- | --- | --- |
| 持久事实 | MySQL 订单、关注边、行为 eventId | 丢失后无法简单推断用户曾做过什么 |
| 查询副本 | 店铺缓存、商家热榜快照 | 事实仍在时可以重新生成 |
| 待完成任务 | Outbox、Stream 未交接消息 | 丢失后可能出现事实存在但后续动作永远不执行 |
| 临时身份/状态 | 验证码、token、限流计数 | 可能失去登录、验证机会或限流窗口 |

一个 Redis Key 不会因为放在 Redis 就自动属于“可删的缓存”。先理解业务责任，才能判断是否可重建。

<a id="section-02-05"></a>

### 用数字走一遍秒杀

演示活动只有 2 张券，用户 A、B、C 依次提交。Lua 给 A 和 B 预占后，Redis 可占库存为 0；C 被拒绝。此时数据库可能仍显示剩余 2，因为后台尚未履约。A 履约成功后 MySQL 变成 1；B 履约成功后变成 0。

中间两种库存暂时不同并不一定错误，它们表达的阶段不同。应结合预占、预约和订单事实解释；不能看见差异就把数据库库存直接复制到 Redis，否则会让 C 再次抢到本来已经分配的资格。

<a id="section-02-06"></a>

### 本章应能画出的最小图

```text
读取：浏览器 → Java → 缓存或 Mapper → 数据 → 浏览器
写入：浏览器 → 身份/规则校验 → 数据库事务 → 结果
异步：数据库待办/Stream → 后台处理 → 持久结果 → 查询状态
```

先用这三条线理解项目，再认识每个中间件。遇到看不懂的术语，问它位于哪条线、负责什么结果，会比背技术名更有效。

## 3. 不同组件各做什么

| 组件 | 初学者理解 | 在这里的用途 |
| --- | --- | --- |
| 浏览器前端 | 用户操作的窗口 | 查店、看笔记、登录、领券、验证亮点 |
| Nginx | 门口的接待员 | 发送静态页面，把 `/api` 请求转给 Java，提供图片 |
| Spring Boot | 处理业务的应用框架 | 接收 HTTP 请求、执行服务、返回 JSON |
| MyBatis-Plus / Mapper | Java 与数据库之间的访问层 | 查询、插入、更新，以及声明复杂 SQL |
| MySQL | 长期保存事实的账本 | 用户、店铺、关系、订单、消息任务和统计事实 |
| Redis | 读写很快的数据结构服务器 | 登录令牌、缓存、锁、Bitmap、GEO、Stream、秒杀预占 |
| Caffeine | Java 进程自己的小缓存 | 减少同一实例反复访问远程缓存 |
| Memcached | 多实例可以共同访问的短缓存 | 位于 Caffeine 与 Redis 数据缓存之间 |
| Canal | 观察数据库变化的订阅者 | 读取 binlog，把店铺和券的变化变成缓存失效 |
| RocketMQ | 可靠业务任务的运输通道 | 秒杀履约、Feed 推送、关系投影、关单等 |
| Kafka | 行为事件的日志通道 | 访问、订单与模拟支付统计，商家热榜 |
| Prometheus / Alertmanager | 测量与告警工具 | 观察积压、失败、延迟和组件不可用 |

“MySQL 是账本”不等于“Redis 随便清空也没关系”。验证码和登录令牌只在 Redis，当前签到也没有数据库备份；秒杀刚被 Lua 受理、尚未登记到 MySQL 的请求还依赖 Redis 持久化。

## 4. 先认识这些基础词

**接口/API**：前端和后端约定好的访问地址。例如 `GET /shop/1` 表示查询 ID 为 1 的店铺；`POST /voucher-order/ordinary/1` 表示提交领取 1 号普通券。GET 常用于读，POST/PUT/DELETE 通常改变状态。项目保留了一个旧的 GET 删图片兼容接口，这是历史兼容，不是新接口的设计建议。

**JSON**：接口传递的文本结构，例如 `{"success":true,"data":{"id":1,"name":"某店"}}`。HTTP 200 只说明请求正常得到响应；还要检查 `success` 和 `errorMsg`，才能判断业务是否成功。

**缓存**：先把读取结果保存一份，下次优先读这份副本。它快，但副本可能过时。因此缓存不适合作为最终的扣库存与付费依据。

**事务**：把若干数据库操作合并成一次提交。例如“保存订单”和“保存订单事件”一起成功或一起失败。这里的 `@Transactional` 管的是 MySQL 数据库事务，不能自动让 Redis、文件和消息队列一起回滚。

**同步与异步**：同步操作在返回前完成；异步操作先受理，再由后台继续处理。异步可以缩短入口等待，但一定要提供状态查询，让用户知道最终结果。

**幂等**：同一个业务动作重复执行，得到的有效结果不重复。例如相同秒杀消息重复消费，不会再扣一次数据库库存。幂等不等于“不允许重试”；恰好相反，它让重试更安全。

**投影**：根据业务事实制作的查询副本。例如数据库里的关注关系可以投影成 Redis Set，数据库中的行为事实可以聚合成商家热榜。

**最终一致性**：一段时间内副本可能落后，但在消息恢复、消费成功后，会趋于正确状态。它不是“任何错误放着都能自己好”；超过重试上限、历史数据丢失等情况需要复核与恢复。

**CDC**：Change Data Capture，捕获数据库变更。在本项目中 Canal 读取 MySQL binlog，识别哪些缓存应该失效。

**ACK**：确认消息已完成某一步。确认的时机决定失败后能不能重试。Stream 接管链路必须在数据库持久交接提交后 ACK，而不是读到消息就 ACK。

**Outbox / Inbox**：Outbox 是生产者保存在数据库里的待投递任务；Inbox 是消费者保存在数据库里的已处理事件登记。一个防丢任务，一个防重复副作用。

## 6. 学习前先确认三个边界

第一，项目仍是一个 Java 应用。拆成 `service`、`cache`、`messaging`、`analytics` 包属于代码分工，不等于微服务拆分。RocketMQ 的部分事件依赖同一个数据库里的任务记录，未来跨服务时需要重新设计消息契约。

第二，消息可能重复、缓存可能暂时过时、组件可能断线。项目的亮点是把这些情况纳入设计，不能据此宣传“零丢失、零重复、永远一致”。

第三，面试可讲的价值来自完整闭环：说明问题，解释选择，指出事实与副本，描述失败恢复，拿验证结果作证。只列出 Redis、Kafka、RocketMQ 三个名字，不能证明掌握了它们。

## 8. 从零建立一套能解释业务的思考方法

<a id="section-08-01"></a>

### 第一次阅读时，先把“一个系统”拆成四个问题

第一次看到 Redis、Canal 和两个消息队列，容易以为需要同时掌握所有组件。先用“打开一家店铺”这个动作提问：用户输入是什么？最终想拿到什么？答案存在哪里？处理失败后用户会看到什么？

输入是店铺 ID，输出是店铺详情。店铺记录的持久来源是 MySQL，缓存保存的是查询副本。如果缓存没有命中，就需要读数据库；如果数据库没有这家店，就应该返回不存在。这里并不需要先知道 RocketMQ 的消费组。沿着一个动作阅读，知识范围自然缩小。

再把动作换成“领取秒杀券”。输入仍然很小，但结果不能只是一份可复制的店铺资料：它会消耗有限资格，还需要生成属于当前用户的订单。此时必须额外问：两个请求同时来会不会超卖？请求返回后后台退出怎么办？重复消费会不会生成两单？组件选择来自这些问题，而不是从组件列表倒推一个业务。

| 问题 | 店铺查询的答案 | 秒杀领取的答案 |
| --- | --- | --- |
| 谁发起 | 匿名或登录访客 | 已登录用户 |
| 主要输入 | 真实店铺 ID | 活动券 ID，用户身份由登录上下文提供 |
| 哪一步改变业务事实 | 查询不改变店铺事实；浏览采集另走分析链路 | Redis 先登记准入资格，数据库随后持久预约并履约 |
| 什么时候可以说完成 | 得到当前可用的详情或明确不存在 | 入口受理后继续观察预约，不能把受理当成订单已落库 |
| 重复执行意味着什么 | 多读一次通常只是多花时间 | 需要识别同一资格，避免多扣库存或重复履约 |

学习其他章节时也照着这五行填写。填不出来的地方，往往就是尚未理解的边界。

<a id="section-08-02"></a>

### 用“账本、复印件、待办单”认识三种数据

把 MySQL 中一张普通订单理解成账本：记录谁以什么价格领取了什么券。店铺缓存像复印件：读取快，内容可以根据账本重新制作。Outbox 则是待办单：订单已经建立，但还有事件历史、延迟关单或分析投递等待处理。

这三个比喻帮助理解恢复方式，却不能直接按产品名字分类。Redis 中的店铺副本能重建，不等于 Redis 中所有内容都能重建。签到位图、登录验证码、尚未完成持久交接的秒杀准入与 Stream 消息，都有自己的生命周期。把 Redis 全部清空可能清掉未完成的责任，不能当成一般缓存修复。

遇到一个 Key 或数据库表，先在纸上写出：谁写它、谁读它、什么时候删它、丢失后从哪里补、有没有已经转交责任的证据。比如行为热榜快照可从分钟桶重算；浏览事件走尽力发送，未成功落地的那一条则未必可以补回。两者都与“统计”有关，恢复保证却不同。

<a id="section-08-03"></a>

### 同步和异步不是快慢两个同义词

同步表示当前调用要等这一步结果，异步表示后续步骤由其他执行过程继续。异步可能降低请求等待，但也新增了“这件事还没完成”的时间段。

以普通领券为例，数据库事务完成后可以返回订单号，后台事件稍后投递。此时订单已经存在，Outbox 还可能 PENDING；不能因消息未完成就告诉用户订单不存在。秒杀入口则更早返回：Lua 准入成功并写入 Stream 后，持久预约与订单仍可能在后续处理。两个接口都返回 ID，业务含义不同。

所以设计返回值时，除了值本身，还要解释状态。浏览采集返回 eventId 只方便追踪；查到事件事实才说明已经消费落库。`success=true` 只说明当前接口定义的步骤成功，阅读接口说明时要找到这个步骤的终点。

<a id="section-08-04"></a>

### 从一个故障反推为什么需要可靠性设计

假设“订单写库成功，然后直接发送消息”。网络发送前 Java 退出，订单留下了，消息却没有。后续重启无法凭进程内变量知道漏了哪一条。把待发送事件写进同一个数据库事务，重启后 Relay 就能继续找到任务。这就是 Outbox 的起点。

再假设消息送达后消费者完成数据库更新，却在回复 Broker 前退出。Broker 会重新投递；如果消费者每次都直接加一，重复就会改变结果。把消费身份与处理结果一同记录，后续才能辨认已经完成的步骤。这是 Inbox 与幂等的起点。

这两个故障不能互相替代：生产端记任务解决“忘了发送”，消费端记身份解决“重复执行”。完整教程会把每个机制对应到一个具体失败窗口，读者也应沿着这个方式理解代码。

### 第一轮学习的交付物

第一轮先不用写新功能。准备一页纸，画出店铺查询、普通领券、秒杀领取三条路径；每条注明同步返回的位置、改变事实的位置和后台未完成任务的位置。再选一条真实订单保存 ID，顺着页面、Controller、Service、Mapper、任务表找到它。

能够指出“这个订单已经存在，但哪个后台事件尚未完成”，比背出所有中间件名称更能证明你读懂了项目。[第 03 章](03-架构代码与数据库.md)继续解释怎样在代码和数据库之间完成这次追踪。
