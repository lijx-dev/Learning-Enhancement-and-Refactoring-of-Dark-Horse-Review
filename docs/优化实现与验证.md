# hm-dianping 优化实现与验证

本轮只修改 hm-dianping，前端沿用 `点评/nginx-1.18.0/html/hmdp` 的默认页面，本轮未修改 CityLens。保留优惠券业务，实现热点缓存、可靠秒杀、状态查询、补偿对账、写接口权限和查询优化；没有迁移 Token 包、额度账本或权益账户。

## 与 token 文档核心亮点的完成度对照

本轮补齐此前缺少的 ScopeCaching、LoadingCache、Memcache、Canal CDC、指标告警与有基线的 HTTP 热点读压测。下表对应 `token秒杀简历包装.md` 与架构图，业务保持优惠券版本。

| 文档目标 | 当前实现 | 验证 |
| --- | --- | --- |
| ScopeCaching 请求内缓存与下层回填 | 过滤器建立 ThreadLocal 作用域；统一入口下层回填；finally 清理；JSON 副本避免共享可变实体 | 正常/异常清理、嵌套作用域、后台线程不继承、请求内命中及修改隔离 |
| Caffeine LoadingCache | 店铺详情、券元数据及券 ID 聚合自动加载，5 秒过期、最多 10,000 条；并发加载合并 | 并发只回源一次、旧加载不能污染新版本 |
| Memcache 跨实例详情缓存 | 五层数据链路；版本命名空间；最多 30 秒且不延长源 TTL；100ms 操作超时与短路回退 | 独立 CacheClient 命中共享数据、旧版本不可达、TTL 边界、故障回退 |
| Canal 订阅 binlog | ROW/FULL；详情失效后读取当前数据库预热；聚合旧/新归属失效；DDL 命名空间失效；广播 JVM；失败 rollback，处理成功并记录审计位点后 ACK | 真实外部 SQL 更新/删除/换店/重连；批次失败不 ACK；避免审计写入的 binlog 自反馈 |
| Lua 原子资格校验、预扣与入队 | 优惠券版本；新增入口结果计数与耗时 | 最后一份库存竞争、重复点击、错误 key 类型关闭入口 |
| Stream 异步事务、pending 接管与幂等 | 独立消费者、唯一约束、事务后 ACK、XCLAIM、退避、身份隔离及毒消息持久化 | 原有秒杀故障回归通过；新增 Redis 7 未投递 lag 指标 |
| 状态、补偿与对账 | PROCESSING/SUCCESS/REVIEW/FAILED、稳定订单号重试、幂等补偿、只读库存对账 | 订单/补偿回放、库存丢失关闭及恢复；人工复核保留 |
| 监控与性能验证 | Prometheus + 本地 Alertmanager、18 条告警；缓存分层、Memcache、CDC、Lua 入口、Stream lag/pending/REVIEW 和 HTTP/消费耗时指标 | 77 项测试通过；HTTP 基线对照；配置校验成功、两个采集目标 up |

Token 包、额度账本和权益账户按用户要求排除。图片生命周期、Feed、普通订单等扩展保持原实现。默认前端仍展示原来的订单 ID，没有新增履约状态界面。

## 数据与状态约定

- `VoucherOrder.status` 仍表示支付/核销/取消状态，兼容原默认页面；履约状态单独保存，不改用 0 来冒充数据库订单。
- `SUCCESS` 只表示订单已持久化。付费券仍可能待支付；免费券为已领取待核销。
- `REVIEW` 表示消息已经可靠转交异常任务，库存和用户资格仍被占用。不能简单把 REVIEW 当失败并直接释放库存。
- 秒杀资格的 `active_user` 生成列只对非 FAILED 记录参与唯一约束。FAILED 历史保留，补偿完成后用户可再次发起新请求。
- 人工重试、补偿和恢复接口都需要管理员身份；管理接口没有自动消费真实资金的能力。
- 恢复接口先将活动置为 PREPARING。发现 Stream 在途任务或 PROCESSING/REVIEW 资格时保持暂停，要求先处理异常。
- 对账只报告差异，不用 Redis 覆盖 MySQL。Redis 与数据库库存差异可能包含尚未登记入库的在途消息。
- 普通订单自动关闭与支付都使用状态条件更新，避免已经支付的订单被超时任务关闭。

## 升级和启动

在 `hm-dianping` 目录执行以下命令，启动独立 MySQL、Redis、Memcached、Canal、RocketMQ、Kafka、Java 和原默认 Nginx 页面：

```bash
docker compose -f dev/docker-compose.yml up -d
```

页面地址：`http://127.0.0.1:8080/`；后端：`http://127.0.0.1:8081/`。默认端口被占用时可设置 `HMDP_WEB_PORT`、`HMDP_API_PORT`。首次下载依赖可能需要数分钟。这个 Compose 使用独立的 `hm-dianping_*` 数据卷，不自动接入已有业务库，不依赖 CityLens 文件。

默认页面的 `/imgs/blogs/...` 图片路径、旧 GET 图片删除请求和点赞 toggle 均由后端兼容；图片归属校验仍生效。新 Redis 缺少课程 GEO 索引时，附近列表从 MySQL 按距离分页查询。页面保持原功能，不额外增加履约状态或运维界面。

Java 启动时自动执行 Flyway，已有数据库以版本 0 建立基线。

1. `V1` 增加秒杀资格、发布基线、死信、Outbox、普通券资格槽、图片归属、审计和关系表，补充订单快照及索引。
2. `V2` 将笔记正文扩展为 TEXT，服务端仍限制 10,000 字符。
3. `V3` 增加活动发布标记，防止 Redis 执行数据丢失后误判成首次发布。
4. `V4` 增加图片生命周期、带路径的删除事件和索引化引用表；回填已登记归属的历史图片引用，兼容默认页面的 `/imgs` 前缀和原始上传路径，路径按字节匹配以兼容旧表排序规则。
5. `V5` 增加 CDC 已处理批次审计表，不修改 V1～V4 的迁移校验和。
6. `V6` 增加 Outbox 领取租约、消费 Inbox、异常消息、订单事件历史、普通订单截止时间；历史未支付普通订单按创建时间加 30 分钟回填。
7. `V7` 增加稳定业务事件唯一键，防止 Stream 重投创建多份秒杀履约事件。
8. `V8` 增加商家快照、行为 Outbox、事件去重事实、分钟热度桶、登录访客事实和 Kafka 异常消息。
9. `V9` 增加分析消息投递时间，支持发送后未消费的对账重投。历史 V1～V8 不修改校验和。

迁移不会删除历史订单。已有订单的快照以迁移时券数据补齐，无法证明历史成交时的价格。原始关注关系按用户和被关注用户去重复制到新关系表，原表保留。原演示点赞计数保留为历史基线，新关系表记录升级后的用户点赞；无法从旧 MySQL 数据恢复没有持久化的历史点赞用户。

**升级旧环境时，先备份 MySQL 与旧 Redis 的 `/data`。** dianping 独立 Compose 配置了 Redis 持久卷和 AOF `appendfsync always`；如果选择迁入已有数据，需明确迁移 MySQL 与 Redis 数据卷，不能把新空卷当成旧环境。已有购买记录而执行状态缺失的活动保持关闭，使用运维接口核对后恢复。Redis 彻底丢失且请求尚未被消费者登记时，仅靠 MySQL 无法找回该请求；不能宣称系统具有跨存储的零丢失或 Exactly Once 保证。

本轮迁移仅执行于隔离测试库和新建的 dianping 本地数据卷，未修改原业务 MySQL 数据卷。

独立 Compose 通过 `HMDP_ADMIN_IDS` 设置管理员白名单，默认无管理权限；通过 `HMDP_PAYMENT_MOCK_ENABLED=true` 启用模拟支付，默认关闭。Java 内部沿用已有的 `citylens.catalog-admin-ids` / `citylens.payment.mock-enabled` 配置键，仅为配置名称，不需要运行或修改 CityLens。

| 接口 | 用途 |
| --- | --- |
| `GET /voucher-order/requests/{orderId}` | 当前用户的秒杀履约结果 |
| `GET /ops/seckill/tasks` | 待核对或失败的持久化请求 |
| `GET /ops/seckill/dead-letters` | 包含格式错误或资格冲突的隔离消息 |
| `POST /ops/seckill/requests/{orderId}/retry` | 将 REVIEW 请求转交 Outbox，按原订单号重试 |
| `POST /ops/seckill/requests/{orderId}/fail` | 确认无法履约，设置 FAILED 并幂等补偿；Redis 暂不可用时可重试 |
| `GET /ops/seckill/{voucherId}/reconcile` | 库存与订单对账，只读 |
| `POST /ops/seckill/{voucherId}/publish` | 发布未使用的新活动 |
| `POST /ops/seckill/{voucherId}/recover` | 核对并恢复已发布活动，不直接覆盖在途任务 |
| `GET /ops/outbox` | 查看待执行和待核对事件 |
| `POST /ops/outbox/{id}/retry` | 重新执行 REVIEW 事件 |
| `GET /actuator/health` | 公开进程健康信息 |
| `GET /actuator/prometheus` | 管理员登录令牌或专用 `Authorization: Bearer ...` 监控凭证；专用凭证仅授权该 GET 接口 |
| `PUT /blog/like/{id}/state?liked=true` | 可幂等的明确点赞状态接口；原 toggle 接口仍兼容 |
| `DELETE /upload/blog?name={path}` | 申请删除本人未被引用的图片；保留默认页面 GET `/upload/blog/delete`，同样校验归属与引用；文件清理由 Outbox 执行 |

请求使用 `authorization` 登录令牌。审计记录管理员写操作的用户、方法、路径、HTTP 状态，不保存令牌或请求正文。业务拒绝仍采用原项目 `success=false` 响应格式。

图片删除接口成功表示删除申请已持久化，此时图片不可再发布。通常下一轮 Outbox 执行会清理文件；文件系统异常会退避重试，超过次数进入 REVIEW，可通过既有 Outbox 运维接口处理。已发布图片通过引用表检查，不再逐次扫描笔记的逗号串。图片归属记录作为删除状态凭据保留，重复删除不会重复创建任务。

## 五层缓存与一致性边界

公共展示数据通过 `CacheClient` 读取。请求级缓存每个请求最多 256 项，后台线程不继承；每次解码得到新实体，优惠券列表填充实时库存不会污染缓存。Caffeine 保存不可变快照并合并并发加载。当前使用全局 JVM generation 隔离失效前后的加载，失效一个 key 会让该实例其他 L1 key 重新进入下层读取；适合课程规模，写入频繁时可改为受控的逐 key generation。

Memcache 使用 `hmdp:<逻辑 key 的 SHA256>:<Redis version>`。失效 Lua 原子递增版本、删除 Redis 数据并广播；晚到的旧 Memcache 写入属于旧版本，新读取无法命中。Memcache 操作故障回退 Redis；首次客户端创建及网络调度不计入严格 100ms SLA。为核对版本，L1 未命中时会先读取 Redis 版本，再读取 Memcache 数据，因此这一层仍依赖 Redis 可用。

展示库存和活动时间窗口通过一次数据库批量查询实时补充，最终购买资格走 Redis Lua 与数据库事务。普通详情缓存不参与交易授权。

空值缓存约 2 分钟，店铺 Redis 详情 TTL 约 20 分钟，券元数据及聚合约 10 分钟，均带抖动。Memcache 快照最多 30 秒且不超过源剩余期限，JVM 最多 5 秒且每次检查快照期限。5 秒仅限制 JVM 独有旧值：CDC 停止或订阅错误时，跨实例旧详情仍可能持续至 Redis TTL，需要告警与核对重放。Pub/Sub 不提供持久投递，丢失通知后由短 TTL 收敛。旧逻辑过期包装保留兼容，公共入口使用互斥加载。

Canal 消费配置 schema 的 `tb_shop`、`tb_voucher`、`tb_seckill_voucher`。重放更新时重新读取当前数据库，不用旧 binlog 行镜像直接覆盖新缓存。优惠券换店同时失效旧、新店铺聚合；删除失效；DDL 使用 SCAN 失效相关命名空间。失败批次 rollback 并重连，重复执行可重放。每个 destination 使用 Redis 主节点锁，其他实例读取共享缓存并接收失效通知。

`tb_cache_cdc_checkpoint` 记录已完成处理的批次、文件及偏移，供审计；实际恢复位点在 Canal `file-instance` 的 `meta.dat`，由 `canal-meta` 持久卷保留，约每秒落盘。崩溃可能重放已处理事件，不能宣称跨存储 Exactly Once。MySQL binlog 保留 7 天，停机超出保留期需要核对并重建基线。订阅使用经过名称校验的 schema 与普通正则，避免 Canal 不兼容的 `Pattern.quote` 写法。只包含无关表事务边界的批次直接 ACK，避免审计写入再次生成 binlog 的自反馈。

非 Docker 启动默认关闭 Memcache/CDC，通过 `HMDP_MEMCACHE_ENABLED/HOST`、`HMDP_CDC_ENABLED/HOST/SCHEMA/DESTINATION` 启用；Compose 默认启用。Canal 镜像为 amd64，Apple Silicon 使用 Docker 架构模拟。

## 本地升级与监控

已存在的独立 dianping MySQL 卷不会重复执行初始化脚本。升级时先启动 MySQL、创建 Canal 读取账号，再启动完整服务；不要为升级删除 MySQL/Redis 卷：

```bash
docker compose -f dev/docker-compose.yml up -d mysql redis
docker compose -f dev/docker-compose.yml exec -T mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"' < dev/mysql/02-canal.sql
docker compose -f dev/docker-compose.yml --profile monitoring up -d
```

新空卷首次初始化自动创建 Canal 账号。脚本密码用于本地独立容器，连接外部环境时需同步修改数据库用户与 Compose 配置。

## RocketMQ 与 Kafka 改造（2026-10-10）

这轮只改点评后端、独立 Compose、测试和本仓库文档。默认页面、CityLens、Token 额度业务保持原范围。

### 实现范围

| 功能 | 当前实现 |
| --- | --- |
| 可靠业务事件 | 本地业务与 Outbox 同事务；短事务用 `FOR UPDATE SKIP LOCKED` 领取任务；批次 UUID、领取租约、过期接管；网络发送在领取事务之外 |
| RocketMQ 分发 | Java 8 兼容的 5.3.2 remoting SDK；Feed、关系、媒体、缓存、活动、履约、订单、截止时间共 8 个消费组；Broker 确认后标记 SENT |
| 消费幂等 | 稳定 Outbox ID；按逻辑消费组＋事件 ID 保存 Inbox；Inbox 与数据库业务效果同事务；快速消费完成时不被发送方覆盖为 SENT |
| Feed 分批 | 每批最多 200 名粉丝，保存游标；续批事件与本批 Inbox 同事务创建，原发布时刻保持一致 |
| 普通订单关单 | 下单保存 `expire_at` 并创建延迟事件；支付、取消与对应事件同事务；条件更新保护状态；提前消息按当前截止时间重新投递；每分钟索引化扫描最多 200 单兜底 |
| 秒杀转交 | Lua 原子受理并写 Stream；消费者登记持久化预占，创建唯一 `seckill:{orderId}` Outbox 后才 ACK Stream；RocketMQ 履约在事务内条件扣库存、创建订单、置 SUCCESS |
| 重试与异常 | 发送端指数退避，10 次失败进入 REVIEW；消费端 Broker 重试，持续失败可靠转交应用异常表后确认；秒杀异常保留库存与资格并进入 REVIEW，人工重试使用原订单号 |
| 投递对账 | 业务消息发送后超过 5 分钟仍未消费时重投；未来截止时间排除；Kafka 订单行为已发送但没有去重事实时重投；事件号保持稳定 |
| Kafka 行为分析 | Kafka 3.9.1 客户端保持 Java 8；单节点 KRaft 本地 Broker；商家 ID 作为 key、3 个分区；消费效果提交后再提交 offset；失败重置整个已拉取批次的各分区起点 |
| 热榜 | 成功商家详情接口访问、普通券下单、模拟支付；事件时间按分钟分桶；5/60 分钟窗口；PV、窗口内去重的登录 UV、下单数、模拟支付数；Redis 快照 5 秒刷新、15 秒 TTL，故障时从持久桶查询 |
| 可观测性 | 消息发送/消费耗时、重试、重复、隔离、Outbox 积压、秒杀转交、Kafka 消费线程与 lag、浏览丢弃、分析 Outbox、事件处理延迟；共 18 条告警 |

### 数据链路

```text
普通业务事务 → 业务 Outbox → RocketMQ → 业务消费者 → Inbox＋数据库效果
普通订单下单 → 截止时间 Outbox → RocketMQ Timer → 条件关单＋OrderClosed
秒杀 Lua → Redis Stream → 持久预占＋唯一 Outbox → ACK Stream
                                      ↓
                                RocketMQ 履约 → 库存＋订单事务
商家详情访问 → 有界后台发送队列 → Kafka → 去重事实＋分钟桶 → Redis 热榜
订单事件消费 → 分析 Outbox      → Kafka → 同上
```

秒杀的转交确认点是 **MySQL Outbox 提交**。Broker 停机后投递任务仍持久保存，不需要在未确认消息是否发送成功时回补库存。与直接 Stream→MQ 桥接不同，这里复用业务 Outbox 做可靠投递，并保存请求的数据库状态。数据库状态是用户履约查询的事实源，Redis 状态是提交后的展示投影。

### 边界与选型

- RocketMQ 使用 remoting SDK 的 `setDeliverTimeMs` 与 Broker Timer Wheel，不使用 gRPC Proxy，也没有将 4.x 固定延迟级别混入当前方案。本地 Broker `SYNC_FLUSH`，延迟范围配置为 24 小时。
- 保留 MySQL 本地消息表。RocketMQ 事务消息可作为选型比较，本轮没有再叠加半消息与事务回查。
- 当前业务消息是薄事件，消费者通过 Outbox 读取持久化业务字段，适用于同库部署。拆成独立服务时需要扩展业务快照与事件契约。
- Inbox 保证数据库效果去重。Redis、文件系统不与 MySQL 原子提交，依赖当前事实投影、版本保护或幂等删除恢复；不宣称跨存储 Exactly-once。
- 商家访问统计是尽力采集：512 项有界后台队列、8 MiB Kafka 缓冲；队列满、进程崩溃或发送失败可丢统计，丢弃有指标。该队列不承载交易任务，也不阻塞详情请求等待 Broker 元数据。
- 普通券下单与模拟支付统计经持久化分析 Outbox 投递。Kafka 生产者幂等不能替代消费者的事件 ID 去重；提交数据库后、提交 offset 前宕机会安全重放。
- 窗口按分钟桶对齐，UV 只统计有登录身份的访问。热度公式为 `PV + 登录UV×2 + 下单×5 + 模拟支付×10`，是演示规则，不是推荐模型或真实成交转化率。Redis 返回榜单最多有刷新周期内的延迟。
- 当前 Kafka 消费端使用数据库事务聚合，方便验证恢复与去重；没有引入 Flink/Kafka Streams，也没有做不同规则的独立投影版本重建。
- 本地 RocketMQ 与 Kafka 都是单 Broker，消息保留 72 小时。去重事实、业务 Outbox 和历史记录暂不自动归档。生产部署需要另行验证副本、故障切换和保留期策略。
- 大 V 拉取合并、点赞事实与异步计数拆分、Canal→Kafka→搜索索引、逐 key 本地缓存版本与 Redis Cluster 同槽拆分仍是后续扩展，本轮没有宣称完成。

### 面试讲法与验证边界

可以围绕三个失败窗口展开：业务已提交但未发送、Broker 已接收但确认丢失、消费数据库已提交但确认未完成。发送端保留稳定事件号，消费端数据库幂等，发送与消费状态可查询；永久失败进入人工任务，库存和资格不被一次超时错误释放。

真实 Broker 集成覆盖重复发送、Timer 关单、支付后延迟消息、Lua/Stream/Outbox/RocketMQ 秒杀履约、Kafka HTTP 访问采集、交易分析投递与重放。发送确认丢失与领取租约恢复通过可控故障模拟验证。没有进行宿主机断电、MQ 多副本切换、长时间阶梯负载或消息保留期耗尽测试；详情缓存短样本不用于证明 MQ 或秒杀容量。

## Mapper 与服务分层规范（2026-10-10）
